Phase 1.5 — Testing Standard

Testing Standard

Standar struktur test, naming convention, test data management, coverage target, dan integrasi CI/CD untuk semua service Rejki Backend.

Phase 1.5 Rust Testing sqlx test

🧭Prinsip

Test behavior, bukan implementationTest harus bisa refactor internal tanpa ubah test. Uji "apa yang dilakukan function", bukan "bagaimana caranya".
Integration test > unit test untuk Rust backendLogic bisnis yang menyentuh DB lebih baik ditest dengan integration test menggunakan DB nyata, bukan mock. Mock DB menghasilkan false confidence.
Test harus idempotenMenjalankan test dua kali berturut-turut harus menghasilkan hasil yang sama. Tidak ada shared state antar test.
Nama test adalah dokumentasiNama test harus cukup deskriptif sehingga pembaca tahu apa yang ditest tanpa baca isi test.
Tidak ada test yang flakyTest yang gagal intermittent wajib diperbaiki atau dihapus. Test flaky lebih berbahaya dari tidak ada test.

🧪Test Tiers

Unit

Unit Test

Test fungsi murni tanpa dependency eksternal. Tidak sentuh DB, tidak kirim HTTP. Cocok untuk: parser, validator, kalkulasi, transformation logic.

Integration

Integration Test

Test alur lengkap dari handler → service → repository dengan DB nyata. Menggunakan PostgreSQL test database yang di-reset setiap test run.

E2E

E2E Test

Test alur end-to-end antar service via HTTP (misal: register → login → buat iklan). Berjalan di CI dengan full docker-compose stack.

🏷️Naming Convention

Format Nama Test

Format: test_{unit}_given_{kondisi}_when_{aksi}_then_{ekspektasi}

Jenis TestContoh Nama
Happy pathtest_login_given_valid_credentials_when_login_then_returns_tokens
Validation errortest_register_given_invalid_email_when_register_then_returns_validation_error
Auth errortest_get_profile_given_no_token_when_request_then_returns_401
Not foundtest_get_job_given_nonexistent_id_when_request_then_returns_404
Business ruletest_apply_job_given_already_applied_when_apply_again_then_returns_conflict
Permissiontest_delete_job_given_other_owners_id_when_delete_then_returns_404
ℹ️
Nama test untuk IDOR case mengembalikan 404, bukan 403

Sesuai standar security-baseline: jika user mencoba akses resource milik orang lain, kembalikan 404 (bukan 403). Ini juga yang harus di-test namanya: _then_returns_404, bukan _then_returns_403.

🧱Test Data

AturanDetail
Setiap integration test buat data sendiriJangan andalkan data yang sudah ada dari test sebelumnya. Setiap test setup data yang dibutuhkan di awal, hapus di akhir (atau rollback transaction).
Gunakan transaction rollback untuk isolasiWrap setiap integration test dalam transaction, rollback di akhir. Lebih cepat dari truncate tabel.
Gunakan fixture factory, bukan hardcodeBuat helper create_test_user(), create_test_job() di tests/common/fixtures.rs. Jangan hardcode UUID atau email di setiap test.
Test email menggunakan domain khususGunakan @test.rejki.internal untuk email test. Tidak akan pernah ada user real dengan domain ini.
Tidak ada data real di testJangan gunakan data dari staging/production dalam test. Semua data test harus generated/fictional.
Contoh Fixture Helper
// tests/common/fixtures.rs
pub async fn create_test_user(pool: &PgPool) -> User {
  let email = format!("test_{}@test.rejki.internal", Uuid::new_v4());
  sqlx::query_as!(
    User,
    "INSERT INTO auth.user (email, password_hash) VALUES ($1, $2) RETURNING *",
    email,
    "$2b$12$hash_placeholder"
  )
  .fetch_one(pool).await
  .expect("failed to create test user")
}

📊Coverage Target

LayerTarget CoverageYang Harus Di-cover
Application (service layer)≥ 80%Semua happy path dan error path dari business logic
Interface (handler layer)≥ 70%Validasi input, auth check, response format
Infrastructure (repository)≥ 60%Query SQL happy path via integration test
⚠️
Coverage 100% bukan tujuan

Target di atas adalah minimum yang bermakna, bukan maksimum. Mengejar 100% coverage sering menghasilkan test yang buruk (test implementation, bukan behavior). Fokus pada test yang bermakna, bukan angka coverage.

📝Contoh Test

Unit Test (Validator)
// src/application/service_test.rs
#[cfg(test)]
mod tests {
  use super::*;

  #[test]
  fn test_validate_email_given_invalid_format_when_validate_then_returns_error() {
    let result = validate_email("not-an-email");
    assert!(result.is_err());
    assert_eq!(result.unwrap_err(), AppError::ValidationError { field: "email".into() });
  }

  #[test]
  fn test_validate_email_given_valid_email_when_validate_then_returns_ok() {
    let result = validate_email("user@example.com");
    assert!(result.is_ok());
  }
}
Integration Test (Handler)
// tests/test_auth_login.rs
#[sqlx::test]    // sqlx::test otomatis buat DB baru dan rollback setelah test
async fn test_login_given_valid_credentials_when_login_then_returns_tokens(
  pool: PgPool
) {
  let app = build_test_app(pool.clone()).await;
  let user = create_test_user(&pool).await;

  let response = app
    .oneshot(Request::post("/api/v1/auth/login")
      .json(json!({ "email": user.email, "password": "test_password" })))
    .await
    .unwrap();

  assert_eq!(response.status(), StatusCode::OK);
  let body: Value = parse_response(response).await;
  assert!(body["success"].as_bool().unwrap());
  assert!(body["data"]["access_token"].is_string());
  assert!(body["data"]["refresh_token"].is_string());
}
