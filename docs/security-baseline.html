Phase 1.5 — Security Baseline

Security Baseline

Dokumen ini mendefinisikan standar keamanan Rejki Backend — apa yang sudah aman sejak Phase 1, apa yang wajib diterapkan di Phase 1.5 sebagai baseline, dan apa yang akan dikeraskan di Phase 3. Keamanan dibangun berlapis, bukan sebagai afterthought.

Phase 1.5 Defense in Depth OWASP Top 10

🗺️Peta Security per Phase

Semua area security diorganisir berdasarkan kapan harus diimplementasi:

✓ Phase 1 — Selesai

JWT RS256 + Token Rotation

Access token (15 mnt) + refresh token rotation. Private key hanya di auth-service. AuthInProcessClient sebagai bridge.

✓ Phase 1 — Selesai

Password Hashing (bcrypt)

bcrypt dengan cost factor default. Password tidak pernah disimpan plaintext. OTP dan refresh token di-hash SHA-256 sebelum masuk DB.

✓ Phase 1 — Selesai

SQL Injection Prevention

100% parameterized query via sqlx. Tidak ada string concatenation untuk SQL. Schema isolation mencegah cross-service data access.

⬤ Phase 1.5 — Baseline

Secret Management Policy

Rules: apa yang boleh/tidak di .env, cara rotasi key JWT, cara handle secret di CI/CD.

⬤ Phase 1.5 — Baseline

Input Sanitization Rules

Whitelist validator per field type. XSS prevention di level response. HTML stripping untuk field text bebas.

⬤ Phase 1.5 — Baseline

File Upload Security

Magic bytes verification, mime whitelist, size limit, path traversal prevention, virus scan (Phase 3).

⬤ Phase 1.5 — Baseline

Security Response Headers

Daftar header yang harus ada: CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy. Diterapkan di nginx.

⬤ Phase 1.5 — Baseline

Error Information Control

Policy: apa yang boleh dikembalikan ke client vs yang hanya boleh ada di log. Stack trace tidak pernah ke client.

◌ Phase 3 — Hardening

Rate Limiting

Per-IP dan per-user rate limit. OTP endpoint: max 5 percobaan/jam. Login endpoint: max 10 percobaan/15 menit.

◌ Phase 3 — Hardening

CORS Production Policy

Restrict origin ke domain resmi. Bukan allow_origin(Any) di production. Credentialed requests harus explicit.

◌ Phase 3 — Hardening

TLS + HSTS

HTTPS-only via Cloudflare Tunnel. HSTS header max-age=31536000; includeSubDomains. No HTTP fallback.

✅ Implemented

Audit Log

Log setiap auth event: login, logout, refresh, failed attempts, OTP sent, password changed, suspend. Log write ke tabel auth.audit_log — append-only, 11 AuditEvent variant, fail-open. W3B-04 · 19 Jun 2026

◌ Phase 3 — Hardening

Enkripsi at Rest

Kolom sensitif (NIK, no. HP) dienkripsi dengan AES-256-GCM sebelum disimpan ke DB. Key disimpan di environment secret.

◌ Phase 3 — Hardening

Dependency Audit

cargo audit di CI/CD untuk cek CVE di dependencies. cargo deny untuk license compliance.

🔐Auth & Token (Phase 1 — Selesai)

KomponenImplementasiAlasan
Access Token JWT RS256, TTL 15 menit RS256 — public key bisa didistribusikan ke service lain tanpa expose private key. TTL pendek minimasi dampak jika token bocor.
Refresh Token 32 random bytes, hex-encoded, SHA-256 di DB, TTL 30 hari Opaque token — tidak bisa di-decode tanpa DB lookup. Hash di DB — jika DB breach, token tidak bisa langsung dipakai.
Token Rotation Old refresh token direvoke sebelum issue new Jika token dicuri dan dipakai duluan, token lama menjadi invalid — mencegah replay attack.
Private Key Hanya ada di auth-service, tidak pernah keluar AuthInProcessClient menjadi bridge — service lain hanya bisa validate via trait, tidak akses key langsung.
Cookie Strategy Refresh token: HttpOnly; Secure; SameSite=Strict Tidak bisa diakses JavaScript — immune terhadap XSS token theft. SameSite=Strict mencegah CSRF.

🔑Password Hashing (Phase 1 — Selesai)

ItemKeputusanKeterangan
AlgoritmabcryptDengan argon2 sebagai upgrade opsional di Phase 3. bcrypt sudah proven dan cukup untuk beban Rejki saat ini.
Cost factorDefault bcrypt (12)~250ms per hash di hardware modern. Cukup lambat untuk brute force, cukup cepat untuk UX normal.
OTP storageSHA-256 di DB, bukan plaintextJika DB breach, OTP yang tersimpan tidak bisa langsung dipakai karena sudah di-hash.
Password resetVia OTP — bukan email link dengan tokenOTP TTL 5 menit, dikonsum atomik (DELETE), tidak bisa replay.
⚠️
Jangan log password

Pastikan tidak ada tracing::debug!("{:?}", body) di handler register/login yang bisa mencetak password ke log. DTO harus implement Debug dengan password di-redact: #[debug(skip)] password: String.

🛡️SQL Injection Prevention (Phase 1 — Selesai)

Yang dilakukan (aman)
// sqlx query! macro — parameterized
sqlx::query!(
  "SELECT * FROM auth.users WHERE email = $1",
  email  // escaped otomatis
).fetch_optional(&pool).await
Yang TIDAK boleh dilakukan
// ❌ JANGAN PERNAH — SQL injection
let q = format!(
  "SELECT * FROM users WHERE email = '{}'",
  email  // tidak di-escape!
);
sqlx::query(&q).fetch_optional(&pool).await
✅
Schema isolation sebagai defense in depth

Setiap service hanya punya akses ke schema-nya sendiri (GRANT USAGE ON SCHEMA auth TO rejki_auth_role). Bahkan jika terjadi injection di satu service, service lain tidak terekspos.

🧹Input Sanitization (Phase 1.5)

Input validation mencegah data tidak valid masuk ke sistem. Input sanitization mencegah data berbahaya mengeksekusi sesuatu yang tidak diinginkan.

Aturan per Tipe Field
Tipe FieldValidasiSanitasi
Email Format RFC 5322, max 254 char Lowercase, trim whitespace
Password Min 8 char, max 128 char Jangan trim (spasi di password valid)
Text bebas (judul, deskripsi) Max length per field, non-empty jika required Strip HTML tags. Trim leading/trailing whitespace. Normalize Unicode (NFC).
UUID Format UUID v4 valid Lowercase
Integer / amount Non-negatif, dalam range i64 Tidak perlu — Rust type system sudah enforce
URL Format URL valid, scheme https:// saja Reject javascript:, data: scheme
Array field Max panjang per konteks, elemen non-empty Deduplicate, trim per elemen
XSS Prevention

Karena Rejki adalah REST API (bukan server-side render HTML), XSS prevention lebih sederhana:

KonteksTindakan
Response Content-TypeSelalu application/json — browser tidak akan execute sebagai HTML
Field teks dari userStrip HTML tags sebelum simpan ke DB. Library: ammonia crate untuk allowlist-based HTML cleaning.
Header X-Content-Type-Optionsnosniff — browser tidak boleh guess content type
URL dari userReject javascript: dan data: scheme di input URL
IDOR Prevention

Insecure Direct Object Reference — user A mengakses data user B hanya dengan mengganti ID di URL.

// ❌ SALAH — tidak cek ownership
pub async fn get_iklan(State(s): State<...>, Path(id): Path<Uuid>) -> ... {
  let iklan = s.service.find_by_id(id).await?;
  Ok(Json(iklan))  // siapapun bisa akses!
}

// ✓ BENAR — cek ownership
pub async fn delete_iklan(
  State(s): State<...>,
  Extension(claims): Extension<AuthClaims>,  // dari auth middleware
  Path(id): Path<Uuid>,
) -> ... {
  // service layer cek: WHERE id = $1 AND owner_id = $2
  s.service.delete(id, claims.sub).await?;
  Ok(StatusCode::NO_CONTENT)
}
💡
Ownership check di application layer, bukan interface

Handler meneruskan user_id dari AuthClaims ke service. Service layer tambahkan AND owner_id = $user_id ke query. Jika tidak match, service return NotFound (bukan Forbidden) — tidak membocorkan informasi bahwa resource ada tapi milik orang lain.

📋Security Response Headers (Phase 1.5)

Header berikut ditambahkan di level nginx (bukan Axum) agar berlaku untuk semua response termasuk static files:

HeaderNilaiMencegah
X-Content-Type-Options nosniff Browser MIME type sniffing — browser tidak boleh mengira JSON adalah HTML
X-Frame-Options DENY Clickjacking — halaman tidak bisa di-embed dalam iframe
Referrer-Policy strict-origin-when-cross-origin Kebocoran URL (dengan token di query param) ke third-party via Referer header
Content-Security-Policy default-src 'none'; frame-ancestors 'none' XSS — untuk API, ini cukup. Frontend Flutter tidak pakai CSP di API response.
Permissions-Policy geolocation=(), microphone=(), camera=() Mencegah halaman yang embed API request mengakses sensor device
Strict-Transport-Security max-age=31536000; includeSubDomains HTTP downgrade attack. Tambahkan di Phase 3 setelah HTTPS production siap.
Cache-Control no-store untuk auth endpoints Token atau data sensitif tersimpan di cache browser / proxy
Konfigurasi nginx (Phase 1.5)
# nginx.dev.conf — tambahkan ke server block
add_header X-Content-Type-Options  "nosniff"          always;
add_header X-Frame-Options          "DENY"             always;
add_header Referrer-Policy          "strict-origin-when-cross-origin" always;
add_header Content-Security-Policy  "default-src 'none'; frame-ancestors 'none'" always;
add_header Permissions-Policy       "geolocation=(), microphone=(), camera=()" always;

# Untuk auth endpoints saja
location /api/v1/auth/ {
  add_header Cache-Control "no-store, no-cache, must-revalidate" always;
  proxy_pass http://rejki_backend;
}

🚫Error Information Control (Phase 1.5)

Informasi yang bocor ke client dalam error response bisa membantu attacker. Atur dengan ketat apa yang boleh dan tidak boleh muncul:

Boleh dikembalikan ke client
✓ error code (SCREAMING_SNAKE_CASE)
✓ error message (human-readable)
✓ field errors (untuk validasi)
✓ request_id (untuk support ticket)
✓ HTTP status code yang tepat
TIDAK boleh dikembalikan ke client
✗ Stack trace Rust
✗ SQL error message (nama tabel, kolom)
✗ Path file di server
✗ Versi library/framework
✗ Internal IP address
✗ Environment variable names
Implementasi di AppError
// common/errors/src/lib.rs
impl IntoResponse for AppError {
  fn into_response(self) -> Response {
    let (status, code, message, fields) = match self {
      AppError::Internal(err) => {
        // Log detail HANYA di server — tidak ke client
        tracing::error!(error = %err, "internal server error");
        (500, "INTERNAL_ERROR", "Terjadi kesalahan internal", None)
      }
      AppError::Validation(fields) =>
        (422, "VALIDATION_ERROR", "Data tidak valid", Some(fields)),
      AppError::NotFound(msg) =>
        (404, "NOT_FOUND", &msg, None),
      // ... variant lain
    };
    // Build response tanpa bocorkan internal detail
  }
}

⏱️Rate Limiting (Phase 3)

Implementasi menggunakan tower-governor crate. Konfigurasi per-endpoint berbeda:

EndpointLimitWindowAlasan
POST /auth/login10 request per IP15 menitCegah credential stuffing
POST /auth/send-otp5 request per IP1 jamCegah SMS/email bombing
POST /auth/verify-otp5 request per sessionPer OTPCegah brute force 6-digit OTP
POST /auth/register3 request per IP1 jamCegah fake account factory
Semua endpoint lain100 request per IP1 menitGeneral DoS protection
💡
Response saat rate limited

HTTP 429 Too Many Requests dengan header Retry-After: 60 (detik). Body menggunakan format error standar: { "success": false, "error": { "code": "RATE_LIMITED", "message": "Terlalu banyak percobaan. Coba lagi dalam 60 detik." } }

🌐CORS Production Policy (Phase 3)

Development (sekarang — longgar)
// rejki-app/src/main.rs
CorsLayer::new()
  .allow_origin(Any)
  .allow_methods(Any)
  .allow_headers(Any)
Production (Phase 3 — ketat)
// Hanya domain resmi
CorsLayer::new()
  .allow_origin([
    "https://rejki.id".parse()?,
    "https://app.rejki.id".parse()?,
  ])
  .allow_credentials(true)
  .allow_headers([AUTHORIZATION, CONTENT_TYPE])
⚠️
allow_credentials(true) tidak kompatibel dengan allow_origin(Any)

Jika menggunakan cookie (refresh token HttpOnly), CORS harus specify origin eksplisit — bukan wildcard. Ini alasan kenapa production config berbeda dari development.

🎭RBAC — Role-Based Access Control (Phase 3)

Multi-tier authorization dengan pure hierarchy rank-based. ✅ Sudah diimplementasi — lihat W3B-05 · ws-multi-tier-rbac.

Hierarchy Rank
RoleRankDB ValueAkses
super_admin100'super_admin'Semua endpoint
admin_iklan80'admin_iklan'Admin iklan + user + moderator + user
admin_user80'admin_user'Admin user/KYC + moderator + user
moderator60'moderator'Report + corporate-comms + user
user_verified40'user_verified'Post iklan, chat, create reports
user20'user' (default)Browse, register, login
Middleware

require_role(min_rank: u8) — Axum middleware via from_fn_with_state. Gantikan require_admin() (binary). Dipasang setelah require_auth. Menolak 403 FORBIDDEN + INSUFFICIENT_ROLE bila rank tidak mencukupi.

Guard per Service
ServiceMin RankRole yang Lolos
auth, user, 4 iklan80super_admin, admin_iklan, admin_user
report, corporate-comms60super_admin, admin_iklan, admin_user, moderator
admin_login gate80super_admin, admin_iklan, admin_user (bukan moderator)
ℹ️
Pure Hierarchy Trade-off

admin_iklan dan admin_user rank sama (80) — bisa akses endpoint satu sama lain. Ini konsekuensi dari model hierarchy murni. Jika diperlukan pemisahan ketat, module-based RBAC bisa dibangun di iterasi berikutnya.

🔒Enkripsi at Rest (Phase 3)

Kolom yang berisi data sangat sensitif dienkripsi sebelum disimpan ke DB, bahkan jika DB breach sekalipun data tidak terbaca tanpa encryption key.

KolomServiceAlasan Dienkripsi
nomor_identitas (NIK/KTP)user-serviceData pribadi sensitif — wajib dilindungi regulasi PDP Indonesia
nomor_hpuser-servicePotensi disalahgunakan untuk spam/phishing jika bocor
rekening_bankuser-serviceData finansial
 
// Algoritma: AES-256-GCM (authenticated encryption)
// Key: baca dari environment variable, panjang 32 byte
// Nonce: 12 byte random per enkripsi (simpan bersama ciphertext)
// Format di DB: base64(nonce || ciphertext || tag)

// Crate: aes-gcm = "0.10"
use aes_gcm::{Aes256Gcm, Key, Nonce};

fn encrypt_field(plaintext: &str, key: &Key<Aes256Gcm>) -> String {
  let nonce = Nonce::from(rand_nonce()); // 12 random bytes
  let ciphertext = cipher.encrypt(&nonce, plaintext.as_bytes());
  base64(nonce + ciphertext)
}
