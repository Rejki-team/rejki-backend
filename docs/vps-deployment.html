Deployment Guide — One-time VPS Setup

Setup VPS untuk Production

Panduan lengkap dari VPS baru hingga aplikasi berjalan di production. Mencakup instalasi Docker, firewall, Cloudflare Tunnel, deploy repo, dan manajemen secrets. Diasumsikan VPS Ubuntu 22.04 / 24.04.

Ubuntu 22.04+ Docker Engine ufw Firewall Cloudflare Tunnel One VPS

⚠️
Build di VPS atau lokal?

Rust build di VPS dengan 1-2 vCPU bisa memakan waktu 5-15 menit. Alternatif yang lebih cepat: build image Docker di mesin lokal, push ke Docker Hub / GitHub Container Registry, lalu pull di VPS. Panduan ini menggunakan build langsung di VPS (lebih simpel untuk awal).

1. Server Setup Awal One-time

Langkah pertama setelah VPS baru — update sistem, buat user non-root, setup SSH key.

Update sistem & install package dasar
bash VPS — sebagai root 
# Update semua package
sudo apt-get update && sudo apt-get upgrade -y

# Install package utilitas dasar
sudo apt-get install -y \
    curl \
    git \
    htop \
    unzip \
    ca-certificates \
    gnupg \
    lsb-release
Buat user deploy (opsional, direkomendasikan)
bash VPS 
# Buat user "deploy" dengan sudo access
sudo useradd -m -s /bin/bash -G sudo deploy

# Set password (atau gunakan SSH key saja)
sudo passwd deploy

# Copy SSH authorized_keys dari root ke user deploy
sudo mkdir -p /home/deploy/.ssh
sudo cp ~/.ssh/authorized_keys /home/deploy/.ssh/
sudo chown -R deploy:deploy /home/deploy/.ssh
sudo chmod 700 /home/deploy/.ssh
sudo chmod 600 /home/deploy/.ssh/authorized_keys
ℹ️
SSH Key Authentication

Pastikan login menggunakan SSH key, bukan password. Setelah setup, pertimbangkan disable password auth di /etc/ssh/sshd_config: set PasswordAuthentication no, lalu sudo systemctl reload sshd.

🐳
2. Install Docker Engine One-time

Gunakan official Docker repo — jangan gunakan apt install docker.io karena versinya sering jauh tertinggal.

bash VPS — install Docker Engine 
# Tambah Docker GPG key
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
    | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# Tambah Docker repository
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Install Docker Engine + Compose plugin
sudo apt-get update
sudo apt-get install -y \
    docker-ce \
    docker-ce-cli \
    containerd.io \
    docker-buildx-plugin \
    docker-compose-plugin

# Tambah user ke group docker (tidak perlu sudo untuk docker)
sudo usermod -aG docker $USER

# Aktifkan Docker daemon saat boot
sudo systemctl enable docker
sudo systemctl start docker

# Verifikasi — logout & login dulu agar group berlaku
docker --version
docker compose version
⚠️
Logout & login setelah usermod -aG docker

Group membership baru berlaku setelah sesi SSH baru. Jalankan newgrp docker untuk langsung aktif tanpa logout, atau tutup dan buka kembali koneksi SSH.

3. Firewall dengan ufw One-time

Prinsip: buka hanya port yang benar-benar dibutuhkan dari luar. Port PostgreSQL (5432) dan Redis (6379) tidak boleh bisa diakses dari internet.

bash VPS — konfigurasi ufw 
# Reset ke default (deny incoming, allow outgoing)
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Izinkan SSH — WAJIB dilakukan sebelum enable, atau terkunci!
sudo ufw allow ssh           # port 22

# Izinkan HTTP — diakses Cloudflare Tunnel dari dalam Docker
# nginx listen :80 dan Tunnel connect ke host port 80
sudo ufw allow 80/tcp

# JANGAN buka 5432 (postgres) atau 6379 (redis) ke internet
# Keduanya hanya perlu diakses antar container di internal network

# Aktifkan firewall
sudo ufw enable

# Verifikasi
sudo ufw status verbose
PortStatusAlasan
22 (SSH)BukaAkses management VPS
80 (HTTP)BukaCloudflare Tunnel connect ke nginx:80 melalui host
443 (HTTPS)Tidak perluHTTPS ditangani Cloudflare — traffic masuk lewat Tunnel, bukan port 443 langsung
5432 (PostgreSQL)TutupHanya diakses antar container di internal network
6379 (Redis)TutupHanya diakses antar container di internal network
8080, 9000TutupService backend — hanya diakses nginx melalui Docker network
ℹ️
docker-compose expose vs ports

Di docker-compose.yml, rejki-app dan bun-notification menggunakan expose bukan ports — artinya port mereka hanya bisa diakses sesama container di network yang sama, tidak di-publish ke host. Ini defense-in-depth tambahan di samping firewall.

⚠️
docker-compose ports 5432 dan 6379 di production

Di docker-compose.yml saat ini, postgres dan redis meng-expose port ke host untuk kemudahan development. Di production, pertimbangkan untuk menghapus baris ports keduanya — ufw sudah memblokir akses luar, tapi defense-in-depth lebih baik.

☁️
4. Setup Cloudflare Tunnel One-time

Cloudflare Tunnel menghubungkan domain ke VPS tanpa membuka port 443 ke internet. HTTPS, DDoS protection, dan CDN ditangani Cloudflare.

1

Login ke Cloudflare Dashboard

Pastikan domain sudah terdaftar di Cloudflare dan nameserver domain sudah diubah ke Cloudflare. Pergi ke Zero Trust → Networks → Tunnels.

2

Buat Tunnel baru

Klik Create a tunnel → pilih Cloudflared → beri nama (contoh: rejki-production) → klik Save tunnel.

3

Copy token tunnel

Cloudflare menampilkan perintah install dengan token. Copy hanya token-nya — panjang string setelah --token. Simpan di .env sebagai CLOUDFLARE_TUNNEL_TOKEN.

bash .env (di VPS) 
CLOUDFLARE_TUNNEL_TOKEN=eyJhIjoiMTIzNDU2Nzg5...
4

Konfigurasi Public Hostname

Di halaman tunnel, tab Public Hostname → Add a public hostname:

FieldNilai
Subdomainapi (atau kosong untuk root domain)
Domainrejki.id (domain kamu)
TypeHTTP
URLnginx:80 atau localhost:80

Karena cloudflare-tunnel container berada di Docker network yang sama dengan nginx, gunakan nginx:80 (nama service Docker) sebagai URL tujuan.

5

Tunnel dijalankan via Docker Compose

Tunnel berjalan sebagai container Docker dengan profiles: [prod]. Tidak perlu install cloudflared di host — cukup jalankan docker compose --profile prod up -d.

✅
Verifikasi

Setelah container berjalan, cek status tunnel di Cloudflare Dashboard — status harus berubah dari Inactive ke Healthy.

6. Setup Secrets & Keys One-time

File-file ini tidak ada di git (sudah di .gitignore) — harus dibuat manual di VPS.

ℹ️
Referensi lengkap env var ada di Config Standard

Bagian di bawah hanya menampilkan nilai production yang perlu diisi. Untuk penjelasan setiap variabel, tipe data, nilai valid, dan prinsip fail-fast, lihat Config Standard — Katalog Variabel.

Buat file .env
bash VPS — /opt/rejki/.env 
# Copy dari .env.example sebagai template
cp .env.example .env
nano .env   # atau vim .env
Isi minimal untuk production
bash .env (production) 
APP_ENV=production

# PostgreSQL
POSTGRES_USER=rejki
POSTGRES_PASSWORD=GANTI_DENGAN_PASSWORD_KUAT
POSTGRES_DB=rejki
DATABASE_URL=postgresql://rejki:GANTI_DENGAN_PASSWORD_KUAT@postgres:5432/rejki

# Redis
REDIS_URL=redis://redis:6379

# JWT
JWT_PRIVATE_KEY_PATH=/app/keys/jwt_private_key.pem
JWT_PUBLIC_KEY_PATH=/app/keys/jwt_public_key.pem

# Firebase (untuk bun-notification-service)
FIREBASE_PROJECT_ID=your-firebase-project-id
FIREBASE_SERVICE_ACCOUNT_PATH=/app/keys/firebase-service-account.json

# Email
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USERNAME=noreply@rejki.id
SMTP_PASSWORD=gmail-app-password
EMAIL_FROM=Rejki <noreply@rejki.id>

# Cloudflare Tunnel
CLOUDFLARE_TUNNEL_TOKEN=token-dari-cloudflare-dashboard
🚨
Permission file .env wajib dibatasi

File .env berisi semua credential. Set permission agar hanya owner yang bisa baca:

bash
chmod 600 .env
ls -la .env
# Output: -rw------- 1 deploy deploy ... .env
Buat direktori keys & isi secrets
bash VPS 
mkdir -p keys
chmod 700 keys

# Generate JWT RSA key pair (jika belum ada)
openssl genrsa -out keys/jwt_private_key.pem 2048
openssl rsa -in keys/jwt_private_key.pem -pubout -out keys/jwt_public_key.pem
chmod 600 keys/jwt_private_key.pem
chmod 644 keys/jwt_public_key.pem
bash VPS — upload Firebase service account 
# Dari mesin lokal — upload file service account ke VPS
scp keys/firebase-service-account.json \
    deploy@YOUR_VPS_IP:/opt/rejki/keys/firebase-service-account.json

# Di VPS — set permission
chmod 600 keys/firebase-service-account.json

Build semua image

8. Update & Redeploy Per Deploy

Langkah manual — digunakan sebelum CI/CD aktif, atau saat hotfix darurat yang tidak bisa menunggu pipeline.

✅
Setelah CI/CD setup, bagian ini tidak perlu dilakukan manual

Push ke main → GitHub Actions otomatis SSH ke VPS dan jalankan langkah-langkah di bawah. Lihat CI/CD Setup. Jalankan manual hanya saat pipeline down atau hotfix mendesak.

bash VPS — redeploy manual (darurat / sebelum CI/CD aktif) 
cd /opt/rejki

# 1. Pull perubahan terbaru
git pull origin main

# 2. Rebuild image yang berubah
docker compose build rejki-app
# Jika bun-notification-service juga berubah:
docker compose build bun-notification

# 3. Restart service dengan image baru
docker compose up -d rejki-app
# Atau restart semua sekaligus:
docker compose --profile prod up -d

# 4. Cek status
docker compose ps
docker compose logs --tail=50 rejki-app
ℹ️
Zero-downtime deployment

Saat ini deployment memerlukan downtime singkat (container lama stop, container baru start). Untuk zero-downtime, perlu setup lebih kompleks (health-check rolling update atau load balancer dua instance). Cukup untuk tahap awal — pertimbangkan di Phase 3 jika dibutuhkan.

9. Monitoring & Log Management
Perintah monitoring harian
bash VPS — monitoring 
# Status semua service
docker compose ps

# Resource usage (CPU, RAM)
docker stats --no-stream

# Log realtime semua service
docker compose logs -f

# Log service tertentu
docker compose logs -f rejki-app
docker compose logs -f bun-notification
docker compose logs -f nginx

# Log N baris terakhir
docker compose logs --tail=100 rejki-app

# Disk usage Docker
docker system df

# Cek Redis Stream
docker compose exec redis redis-cli XLEN notifications_stream
docker compose exec redis redis-cli XLEN notifications_dlq   # dead letter queue

# Cek koneksi PostgreSQL aktif
docker compose exec postgres psql -U rejki -d rejki \
    -c "SELECT count(*) FROM pg_stat_activity;"
Log rotation

Docker menyimpan log container di host. Tanpa konfigurasi, log bisa tumbuh tidak terbatas. Tambahkan konfigurasi log rotation ke Docker daemon:

json /etc/docker/daemon.json 
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "5"
  }
}
bash
# Apply konfigurasi daemon.json
sudo systemctl reload docker

# Container yang sudah berjalan perlu di-recreate untuk pakai setting baru
docker compose down && docker compose --profile prod up -d
⚠️
Monitor dead letter queue (DLQ)

Jika XLEN notifications_dlq terus bertambah, artinya ada notifikasi yang gagal dikirim setelah semua retry. Perlu investigasi — kemungkinan FCM token semua expired, koneksi Firebase bermasalah, atau format event salah.

Disk cleanup berkala
bash VPS — cleanup Docker resources tidak terpakai 
# Hapus image lama, container stopped, network tidak terpakai
# AMAN — tidak menyentuh container yang sedang berjalan
docker system prune -f

# Jika mau hapus semua image tidak dipakai juga
docker system prune -af  # ⚠️ akan re-download image saat rebuild

10. Dev & Prod di Satu VPS — Tanpa Staging

Karena hanya ada satu VPS dan tidak ada staging server, dev dan prod dijalankan sebagai dua instance Docker Compose terpisah di direktori berbeda, dengan port berbeda, dan database berbeda.

⚠️
Risiko satu VPS: resource berbagi

Dev dan prod berbagi CPU dan RAM. Build Rust di sisi dev bisa mempengaruhi performa prod. Lakukan build di jam sepi, atau build lokal lalu push image ke registry.

Struktur direktori
bash VPS — layout direktori 
/opt/rejki/
├── prod/          # production — branch: main
│   ├── .env       # APP_ENV=production
│   ├── keys/
│   └── ...        # clone repo prod
└── dev/           # development — branch: develop
    ├── .env       # APP_ENV=development
    ├── keys/
    └── ...        # clone repo dev
Setup direktori
bash VPS 
sudo mkdir -p /opt/rejki/{prod,dev}
sudo chown -R deploy:deploy /opt/rejki

# Clone production (branch main)
cd /opt/rejki/prod
git clone -b main https://github.com/YOUR_USERNAME/rejki-backend.git .

# Clone development (branch develop)
cd /opt/rejki/dev
git clone -b develop https://github.com/YOUR_USERNAME/rejki-backend.git .
Port allocation — dev dan prod tidak bertabrakan
ServiceProduction port (host)Development port (host)
nginx808080
PostgreSQL54325433
Redis63796380
Pembeda dev vs prod — sisanya setara

Di konteks VPS, konfigurasi dev dan prod pada dasarnya sama. Yang membedakan hanya tiga hal berikut; selebihnya identik (struktur variabel, image, layout).

AspekDevProd
DomainSubdomain — mis. dev.rejki.idDomain utama — mis. rejki.id
Swagger UIAda — /swagger-ui + /api-docs/openapi.json (otomatis dari APP_ENV=development)Tidak ada — kedua rute tidak dipasang (404), skema API tidak terekspos
nginxnginx.dev.confnginx.prod.conf — tambah rate limiting & JSON logging
Swagger di-gate oleh APP_ENV, bukan oleh nginx. Saat APP_ENV=production, rejki-app tidak mendaftarkan rute Swagger sama sekali — baik UI (/swagger-ui) maupun dokumen (/api-docs/openapi.json) mengembalikan 404. Tidak ada variable khusus untuk mengaktifkan/menonaktifkan Swagger.
Secret & variable GitHub Actions seragam. Karena struktur konfigurasi dev & prod sama, gunakan kumpulan secret/variable yang sama untuk kedua environment; yang berbeda hanya nilai environment-specific (domain/subdomain, APP_ENV, token Cloudflare Tunnel). Tambahkan variable baru ke kedua environment agar paritas terjaga. Lihat CI/CD Setup.
docker-compose.override.yml untuk dev

Buat file docker-compose.override.yml di direktori dev/ — Docker Compose otomatis merge file ini dengan docker-compose.yml utama. Tidak perlu modifikasi docker-compose.yml utama.

yaml /opt/rejki/dev/docker-compose.override.yml 
# Override port untuk dev — tidak bertabrakan dengan prod
services:
  postgres:
    ports:
      - "5433:5432"   # dev postgres di host port 5433

  redis:
    ports:
      - "6380:6379"   # dev redis di host port 6380

  nginx:
    ports:
      - "8080:80"     # dev nginx di host port 8080
    volumes:
      - ./nginx.dev.conf:/etc/nginx/conf.d/default.conf:ro  # pastikan pakai dev config
.env untuk masing-masing environment
bash /opt/rejki/prod/.env 
APP_ENV=production

# ... var dev lainnya (boleh pakai kredensial test)
🚨
Database dev dan prod harus terpisah

Dev menggunakan POSTGRES_DB=rejki_dev, prod menggunakan POSTGRES_DB=rejki. Meski berada di container PostgreSQL berbeda (satu di /opt/rejki/prod, satu di /opt/rejki/dev), pastikan DATABASE_URL masing-masing menunjuk ke database yang benar. Data prod tidak boleh tercampur dengan dev.

Docker Compose project name — cegah nama container bentrok

Docker Compose memberi nama container berdasarkan nama direktori + nama service. Karena dua direktori berbeda (prod/ dan dev/), nama container otomatis berbeda. Tapi lebih eksplisit menggunakan -p flag atau file .env:

bash Cara menjalankan 
# Production — dengan Cloudflare Tunnel
cd /opt/rejki/prod
docker compose -p rejki-prod --profile prod up -d

# Development — tanpa Cloudflare Tunnel
cd /opt/rejki/dev
docker compose -p rejki-dev up -d

# Lihat semua container (dari direktori manapun)
docker ps

# Log production
docker compose -p rejki-prod logs -f rejki-app

# Log development
docker compose -p rejki-dev logs -f rejki-app
Akses dev dari luar & pengamanan Swagger

Karena dev memiliki Swagger UI (peta lengkap API), akses dev tidak boleh publik. Mengikuti praktik industri (pertahanan berlapis untuk dokumentasi API non-produksi):

  • Gate environment — Swagger absen total di prod (sudah otomatis dari APP_ENV).
  • Batasi jaringan dev — default: subdomain dev (dev.rejki.id) di belakang Cloudflare Access (SSO + audit, tanpa shared secret). Lebih baik daripada basic-auth nginx. Alternatif tanpa subdomain publik: SSH tunnel sementara (di bawah).
  • Selalu HTTPS — ditangani Cloudflare.
  • Lindungi juga openapi.json, bukan hanya UI — pembatasan jaringan berlaku ke seluruh subdomain dev, sehingga dokumen skema tidak bisa ditarik langsung.

Dev tidak memerlukan Cloudflare Tunnel untuk produksi. Untuk akses dev cepat dari laptop tanpa mengekspos subdomain, gunakan SSH tunnel sementara:

bash Mesin lokal — SSH tunnel ke dev di VPS 
# Forward localhost:18080 → VPS:8080 (nginx dev)
ssh -L 18080:localhost:8080 deploy@YOUR_VPS_IP -N

# Akses di browser/Postman:
# http://localhost:18080/api/v1/...
Workflow deploy — dev ke prod

Karena tidak ada staging, alur pengujian dilakukan di environment dev di VPS yang sama, sebelum merge ke main dan deploy ke prod:

bash Alur kerja 
── 1. Kerjakan fitur di branch feature/xxx ──────────────────────
# Di mesin lokal
git checkout -b feature/notif-push
# ... coding ...
git push origin feature/notif-push

── 2. Deploy ke dev di VPS untuk testing ────────────────────────
cd /opt/rejki/dev
git fetch origin
git checkout develop
git merge feature/notif-push     # atau via PR ke develop
docker compose -p rejki-dev build rejki-app
docker compose -p rejki-dev up -d rejki-app
# Test via SSH tunnel dari mesin lokal

── 3. Jika OK, merge ke main dan deploy prod ─────────────────────
# Merge develop → main (via PR atau langsung)
cd /opt/rejki/prod
git pull origin main
docker compose -p rejki-prod build rejki-app
docker compose -p rejki-prod up -d rejki-app

# Verifikasi prod
curl https://api.rejki.id/health
ufw — buka port 8080 untuk dev (opsional)

Jika ingin akses langsung ke dev dari luar VPS tanpa SSH tunnel (misalnya akses dari IP tertentu saja):

bash VPS — opsional, hanya jika dibutuhkan 
# Buka port 8080 HANYA dari IP tertentu (IP kantor/rumah)
sudo ufw allow from YOUR_IP_ADDRESS to any port 8080

# JANGAN buka 8080 untuk semua IP di production VPS
# Lebih aman: gunakan SSH tunnel (lihat di atas)
✅
Ringkasan: Dev vs Prod di satu VPS

Prod di /opt/rejki/prod → nginx port 80 → Cloudflare Tunnel → internet. Dev di /opt/rejki/dev → nginx port 8080 → akses via SSH tunnel dari lokal. Database terpisah (rejki vs rejki_dev). Kedua instance berjalan bersamaan tanpa konflik berkat project name berbeda (-p rejki-prod vs -p rejki-dev).
