Phase 1.5 — Authorization Pattern

Authorization Pattern

Standar 3 lapisan otorisasi — autentikasi JWT, ownership check, dan visibility rule — beserta pola implementasi Rust yang konsisten di semua service Rejki Backend.

Phase 1.5 Security

🧭Prinsip

Autentikasi di middleware, otorisasi di handler/repositoryJWT validation (autentikasi) dilakukan oleh AuthMiddleware sebelum request sampai ke handler. Pengecekan siapa boleh akses apa (otorisasi) dilakukan di handler atau repository — bukan di middleware.
Kembalikan 404, bukan 403 untuk IDORJika user mencoba mengakses resource milik orang lain, kembalikan 404 Not Found — bukan 403 Forbidden. Ini mencegah resource enumeration (attacker tidak tahu apakah resource ada atau tidak).
Ownership check di repository layerQuery SQL wajib menyertakan AND owner_id = $caller_user_id. Jangan lakukan ownership check di handler dengan SELECT dulu lalu compare — ini race condition dan lebih lambat.
Public resource tidak butuh authIklan yang sudah diterbitkan bisa dilihat tanpa login. Handler untuk resource publik tidak perlu AuthMiddleware, tapi tetap tidak boleh mengembalikan data sensitif milik pemilik.

👤Ownership Check

Pola Query Ownership di Repository
Benar
-- Ownership check di dalam query
SELECT * FROM job.job_listing
WHERE id = $1
  AND owner_id = $2         -- $2 = claims.user_id
  AND deleted_at IS NULL;

-- Jika tidak ada row → return 404
-- Bisa karena id tidak ada, ATAU
-- id ada tapi bukan milik caller
Salah
-- JANGAN: SELECT dulu, compare di Rust
SELECT * FROM job.job_listing
WHERE id = $1;

// lalu di Rust:
if listing.owner_id != claims.user_id {
  return Err(AppError::Forbidden); // ← SALAH
}
// race condition + bocorkan 403
OperasiQuery Pattern
GET resource milik sendiriWHERE id = $1 AND owner_id = $2 AND deleted_at IS NULL
UPDATE resource milik sendiriWHERE id = $1 AND owner_id = $2 AND deleted_at IS NULL + SET updated_at = now()
DELETE (soft) resource milik sendiriWHERE id = $1 AND owner_id = $2 AND deleted_at IS NULL + SET deleted_at = now()
GET resource publik (tanpa auth)WHERE id = $1 AND is_published = true AND deleted_at IS NULL (tidak cek owner_id)

🚫
403 Forbidden hanya untuk pembatasan fitur, bukan IDOR

Contoh 403 yang benar: user tier gratis mencoba akses fitur premium. Contoh 403 yang salah: user A mencoba delete iklan milik user B — ini harus 404. Memberikan 403 untuk IDOR memberitahu attacker bahwa resource ada.

⚙️Implementasi Rust

// iklan-pekerjaan-service/src/infrastructure/repository.rs
pub async fn find_by_id_and_owner(
  &self,
  id: Uuid,
  owner_id: Uuid,            // dari claims.user_id
) -> Result<JobListing, AppError> {
  sqlx::query_as!(
    JobListing,
    "SELECT * FROM job.job_listing WHERE id = $1 AND owner_id = $2 AND deleted_at IS NULL",
    id, owner_id
  )
  .fetch_optional(&self.pool).await?
  .ok_or(AppError::NotFound)   // 404 — tidak peduli alasannya
}

// Untuk resource publik: tidak ada owner check
pub async fn find_published(&self, id: Uuid) -> Result<JobListing, AppError> {
  sqlx::query_as!(
    JobListing,
    "SELECT * FROM job.job_listing WHERE id = $1 AND is_published = true AND deleted_at IS NULL",
    id
  )
  .fetch_optional(&self.pool).await?
  .ok_or(AppError::NotFound)
}

// Handler — visibility rule setelah ownership check
pub async fn get_job_handler(
  Extension(claims): Extension<AuthClaims>,
  Path(id): Path<Uuid>,
  State(service): State<JobService>,
) -> impl IntoResponse {
  let listing = service.get_by_id_and_owner(id, claims.user_id).await?;
  ApiResponse::ok(listing)  // semua field untuk pemilik
}

🎭Role-Based Access Control (Lapisan 4 — Phase 3)

Setelah autentikasi (Lapisan 1) dan ownership check (Lapisan 2), ada lapisan tambahan untuk membedakan akses berdasarkan role pengguna. ✅ Sudah diimplementasi — W3B-05 ws-multi-tier-rbac.

Role Hierarchy (Rank-based)

Setiap role memiliki rank numerik. Otorisasi = request.role.rank() >= endpoint.min_rank.

RoleRankAkses
super_admin100Semua endpoint (ALL)
admin_iklan / admin_user80Admin endpoint iklan/user + moderator + user
moderator60Report + corporate-comms + user
user_verified40Post iklan, chat, create reports
user20Browse, register, login (default)
Middleware: require_role(min_rank)

Menggantikan require_admin() (binary old). Factory function via axum::middleware::from_fn_with_state.

// Dipasang di router setelah require_auth:
.layer(axum::middleware::from_fn_with_state(80u8, require_role))
// 80 = admin_iklan/admin_user ke atas. 60 = moderator ke atas.

// Penolakan otomatis → 403 FORBIDDEN + INSUFFICIENT_ROLE
// Tidak membedakan "role tidak cukup" vs "bukan admin" — aman dari information leak.
Idempoten Ownership Check Tetap Berlaku

Role check (Lapisan 4) adalah gating tambahan — tidak menggantikan ownership check di SQL (Lapisan 2). Setelah lolos role gate, endpoint tetap harus memverifikasi kepemilikan resource. IDOR tetap 404, bukan 403.

ℹ️
Testing Pattern

Format: test_{endpoint}_given_{role}_when_access_{resource}_then_{status}. Contoh: test_suspend_given_moderator_when_suspend_user_then_403.
