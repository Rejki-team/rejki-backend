Rejki Backend
Modular Monolith

Sistem backend yang didesain sebagai Modular Monolith — semua service berjalan dalam satu process, namun setiap domain terisolasi penuh dan siap diekstrak menjadi microservice tanpa perubahan pada business logic.

🦀 Rust 🐘 PostgreSQL 📦 Modular Monolith ⚡ Stateless

⚡Stateless Service Design

🎫

JWT Authentication

Token self-contained RS256. Server tidak simpan session. Validasi JWT dipusatkan via AuthClient trait — private key hanya ada di auth-service.

💾

State di Database

Semua state persisten ada di PostgreSQL. Tidak ada in-memory state yang di-share antar request.

🔄

Horizontal Scaling

Karena stateless, instance bisa di-scale bebas. Restart tanpa koordinasi.

⏱️

Redis (opsional)

Untuk rate limiting, token blacklist, dan WebSocket pub/sub (multi-replica chat).

💡
OTP disimpan di auth-service

OTP adalah bagian dari authentication flow. Disimpan di tabel auth.otp_verifications dengan kolom expires_at. Pengiriman OTP dilakukan via notification-service-client — auth-service tidak tahu provider pengiriman.

⚠️
Extraction path via trait swap

Saat service diekstrak, hanya implementasi trait yang berubah — dari direct function call menjadi HTTP/gRPC client. Consumer (service yang pakai) tidak perlu diubah sama sekali.

🐘Database Strategy

📂

Schema Isolation

Setiap service punya PostgreSQL schema sendiri: auth.*, user_svc.*, chat.*, dst. Tidak ada tabel yang diakses lintas service.

🚫

No Cross-Service FK

Foreign key hanya dalam satu schema. Konsistensi referensial dijaga di application layer, bukan DB constraint.

🆔

UUID v7

Semua primary key UUID v7 (time-sortable). Setiap service generate ID sendiri tanpa koordinasi ke DB.

🔄

Migration Isolated

Setiap service kelola migration sendiri di folder migrations/. Dijalankan otomatis via sqlx::migrate!() saat startup.

🔌

Connection Pool Terpisah

sqlx::PgPool per service — memudahkan ekstraksi ke DB terpisah di masa depan.

📋

Denormalized Read

Data dari domain lain disimpan sebagai denormalized copy lokal. Update via event atau re-fetch — tidak pernah JOIN lintas schema.

🚫
Aturan emas database

Jika ada kebutuhan JOIN antara tabel milik dua service berbeda, itu sinyal boundary service salah. Perbaiki boundary-nya, jangan tambah JOIN-nya.

📐Prinsip Desain

01

Service Independence

Tidak ada import langsung antar service. Komunikasi hanya via *-service-client trait.

02

Minimal Surface Client Domain

Client domain hanya ekspos yang benar-benar dibutuhkan konsumer. Internal model, repo, logic tetap tersembunyi.

03

Composition Root Tunggal

rejki-app adalah satu-satunya tempat wiring terjadi. Service tidak tahu siapa yang menggunakannya.

04

Stateless Service

Tidak ada state di memory service. State ada di PostgreSQL. Mendukung horizontal scaling dan restart bebas.

05

No Cross-Service DB Join

Setiap service punya schema tabel sendiri. Tidak ada foreign key antar service.

06

Extraction-Ready by Design

Setiap service bisa diekstrak ke process terpisah kapan saja: (1) swap trait impl, (2) pisah DB schema, (3) deploy binary standalone.
