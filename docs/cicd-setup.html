Phase 1.5 — CI/CD Setup

GitHub Actions — CI & CD

Tiga workflow: CI (format + clippy + build + test pada setiap PR), Deploy Dev (push ke develop → VPS dev otomatis), dan Deploy Prod (push ke main → VPS prod otomatis). Tidak ada staging server — dev dan prod di VPS yang sama.

GitHub Actions cargo clippy cargo test SSH Deploy Docker Build Cache
📋
Overview: 3 Workflow
FileTriggerJobsTujuan
.github/workflows/ci.yml Push / PR ke develop atau main check → test → docker-build-check Gate wajib — kode tidak bisa masuk tanpa lulus CI
.github/workflows/deploy-dev.yml Push ke develop atau manual (workflow_dispatch) deploy-dev Deploy otomatis ke /opt/rejki/dev di VPS
.github/workflows/deploy.yml Push ke main deploy Deploy otomatis ke /opt/rejki/prod di VPS
ℹ️
CI harus lulus sebelum deploy bisa berjalan

Deploy prod hanya trigger saat push ke main. Merge ke main sebaiknya hanya dilakukan via PR yang sudah lulus CI — enforce ini dengan branch protection rule di GitHub (lihat Branch Strategy).

📄
Workflow Files
ci.yml — Check + Test

Tiga job yang berjalan berurutan: check → test → docker-build-check (hanya di PR ke main).

JobLangkahCatatan
check cargo fmt --check → cargo clippy -D warnings → cargo build Gagal jika ada warning clippy atau kode tidak diformat
test cargo test --workspace Berjalan setelah check lulus. APP_ENV=development di-set agar tidak panic.
docker-build-check Build dua Docker image tanpa push Hanya di push/PR ke main — tidak perlu tiap PR ke develop
⚠️
Rust build cache — wajib untuk kecepatan

Swatinem/rust-cache@v2 men-cache direktori ~/.cargo dan target/ antar run. Tanpa cache, setiap CI run compile ulang semua dependency (~5-10 menit). Dengan cache, hanya recompile yang berubah (~1-2 menit).

deploy.yml — Production Deploy
yaml .github/workflows/deploy.yml (script bagian utama) 
script: |
  set -e                          # exit jika ada perintah gagal

  cd /opt/rejki/prod
  git pull origin main            # ambil commit terbaru

  docker compose -p rejki-prod build rejki-app
  docker compose -p rejki-prod build bun-notification

  docker compose -p rejki-prod --profile prod up -d

  sleep 10                        # tunggu service start
  curl -sf http://localhost/health || exit 1   # verifikasi

  docker image prune -f           # bersihkan image lama
✅
concurrency: cancel-in-progress: false untuk prod

Jika ada dua push ke main hampir bersamaan, deployment kedua menunggu deployment pertama selesai — tidak dibatalkan. Ini mencegah race condition di VPS.

deploy-dev.yml — Dev Deploy

Sama seperti prod tapi target /opt/rejki/dev dan port 8080. Menggunakan cancel-in-progress: true — jika push cepat berturut-turut, deploy lama dibatalkan dan langsung pakai yang terbaru.

Juga mendukung workflow_dispatch — bisa di-trigger manual dari tab Actions GitHub tanpa harus push.

🚨
Jangan gunakan SSH key yang sama dengan akses personal

Buat SSH key pair khusus untuk GitHub Actions (deploy key). Jika key bocor, revoke hanya key itu — akses personal tidak terdampak.

🌍
GitHub Environments

Workflow deploy menggunakan environment: production dan environment: development. Environment di GitHub memberikan proteksi tambahan: required reviewers, wait timer, dan environment-specific secrets.

Buka GitHub repo → Settings → Environments → New environment:

EnvironmentProtection Rules (rekomendasi)
production Required reviewers: 1 (kamu sendiri) — deploy prod butuh approval manual. Deployment branches: main saja.
development Tanpa protection — deploy dev bisa langsung otomatis. Deployment branches: develop saja.
ℹ️
Required reviewer untuk production (opsional tapi direkomendasikan)

Dengan required reviewer diaktifkan, workflow deploy prod akan pause dan menunggu approval sebelum SSH ke VPS. Kamu review deployment tersebut lalu klik Approve. Cocok untuk mencegah deploy tidak sengaja.

🔁
Secret & variable seragam untuk dev dan prod

Karena dev dan prod memakai struktur konfigurasi yang sama (lihat VPS Deployment §10), kumpulan secret/variable kedua environment juga sama — yang berbeda hanya nilai-nya:

  • APP_ENV → development (dev) / production (prod). Ini juga yang menentukan ketersediaan Swagger UI — dev punya, prod tidak.
  • Domain → subdomain (mis. dev.rejki.id) untuk dev / domain utama (mis. rejki.id) untuk prod.
  • CLOUDFLARE_TUNNEL_TOKEN → token tunnel masing-masing (dev opsional bila tidak mengekspos subdomain publik).
  • Kredensial DB → database/port berbeda per environment.

Saat menambahkan variable baru, tambahkan ke kedua environment (dengan nilai sesuai) agar paritas konfigurasi terjaga dan tidak ada drift antar environment.

Apa yang terjadi di VPS saat deploy prod
bash SSH script yang dijalankan GitHub Actions 
cd /opt/rejki/prod

git pull origin main              # pull commit terbaru

# Build image baru — pakai Docker layer cache
# Jika hanya source yang berubah (bukan Cargo.toml), build ~2-5 menit
docker compose -p rejki-prod build rejki-app
docker compose -p rejki-prod build bun-notification

# Restart dengan image baru — brief downtime ~5-10 detik
docker compose -p rejki-prod --profile prod up -d

sleep 10
curl -sf http://localhost/health  # gagal = workflow error = notif ke GitHub

docker image prune -f             # bersihkan image lama, hemat disk
⚠️
Brief downtime saat deploy

Ada downtime ~5-10 detik saat container lama stop dan container baru start. Untuk production dengan traffic rendah di awal ini bisa diterima. Zero-downtime deployment (rolling update) bisa diimplementasi di Phase 3 jika dibutuhkan.

🗝️
Setup SSH Deploy Key

GitHub Actions butuh SSH key untuk masuk ke VPS. Buat key pair baru khusus untuk CI/CD — jangan reuse key personal.

1. Generate key pair (di mesin lokal)
bash Mesin lokal 
# Generate key pair khusus GitHub Actions
ssh-keygen -t ed25519 -C "github-actions-rejki" -f ~/.ssh/rejki_deploy_key -N ""

# Dua file dihasilkan:
# ~/.ssh/rejki_deploy_key      ← private key (masuk ke GitHub Secrets)
# ~/.ssh/rejki_deploy_key.pub  ← public key (masuk ke VPS authorized_keys)
2. Daftarkan public key ke VPS
bash Mesin lokal → VPS 
# Copy public key ke VPS
ssh-copy-id -i ~/.ssh/rejki_deploy_key.pub deploy@YOUR_VPS_IP

# Atau manual — tambahkan isi .pub ke VPS:
cat ~/.ssh/rejki_deploy_key.pub
# Paste isi di atas ke /home/deploy/.ssh/authorized_keys di VPS
3. Simpan private key ke GitHub Secrets
bash Mesin lokal — tampilkan private key 
cat ~/.ssh/rejki_deploy_key

Copy seluruh output (termasuk baris -----BEGIN OPENSSH PRIVATE KEY----- dan -----END OPENSSH PRIVATE KEY-----) dan paste sebagai nilai secret VPS_SSH_KEY di GitHub.

4. Verifikasi koneksi
bash Mesin lokal — test koneksi dengan deploy key 
ssh -i ~/.ssh/rejki_deploy_key deploy@YOUR_VPS_IP "docker compose --version"
# Harus output versi Docker Compose tanpa error
✅
Setelah verifikasi berhasil

Hapus atau simpan private key di tempat aman — key ini hanya perlu di GitHub Secrets. Tidak perlu di mesin lokal setelah setup selesai.
