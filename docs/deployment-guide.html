📦 Rejki — Deployment Guide

Panduan step-by-step untuk mendeploy Rejki Backend (Rust) + Rejki Web (Vue 3) ke VPS.
Images di-push ke GitHub Container Registry (GHCR) — server hanya pull & restart.

ghcr.io docker compose cloudflare tunnel postgres redis

💡
Kenapa pakai GHCR? Kenapa tidak clone repo di server?

Tidak clone repo di server — lebih aman, tidak ada source code di VPS.
Tidak build di server — server tidak perlu Rust toolchain (hemat 1-2GB).
Deploy lebih cepat — pull image jauh lebih cepat daripada build dari source.
Reproducible — image yang di-push sudah terverifikasi oleh CI.

Cara buat GHCR_TOKEN:

  1. GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic)
  2. Buat token baru dengan scope: read:packages, write:packages, delete:packages
  3. Copy token dan simpan sebagai secret GHCR_TOKEN di repo

  3. Centang: Allow GitHub Actions to create and approve pull requests

4 Setup SSH Key untuk GitHub Actions

GitHub Actions perlu akses SSH ke VPS untuk menjalankan perintah deploy.

4.1 Generate SSH key pair (di VPS atau lokal)

ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/github-actions
# Ini menghasilkan 2 file:
#   ~/.ssh/github-actions      (private key)
#   ~/.ssh/github-actions.pub  (public key)

4.2 Tambahkan public key ke VPS

# Di VPS:
cat ~/.ssh/github-actions.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

4.3 Tambahkan private key ke GitHub Secrets

  1. Copy isi file private key: cat ~/.ssh/github-actions
  2. Buka repo → Settings → Secrets and variables → Actions
  3. Buat secret baru: VPS_SSH_KEY → paste private key
⚠️
Format private key harus tepat

Pastikan private key diawali dengan -----BEGIN OPENSSH PRIVATE KEY----- dan diakhiri -----END OPENSSH PRIVATE KEY-----. Jangan ada spasi ekstra.

5 Deploy Infrastructure

Infrastructure (PostgreSQL, Redis, MinIO, ClamAV) adalah shared component yang digunakan oleh dev dan prod.

💡
Infrastructure cukup di-deploy SEKALI

PostgreSQL, Redis, dan MinIO di-deploy sekali di awal. Tidak perlu di-deploy ulang setiap update backend.

5.1 Buat direktori infrastructure

sudo mkdir -p /opt/rejki/{infra,dev,prod,keys,scripts}
sudo chown -R $USER:$USER /opt/rejki

5.2 Copy file docker-compose infrastructure

File docker-compose.infra.yml ada di repo backend. Copy ke server:

# Dari lokal, SCP file infra ke server:
scp docker-compose.infra.yml user@vps:/opt/rejki/infra/docker-compose.infra.yml

# Atau buat manual di server:
nano /opt/rejki/infra/docker-compose.infra.yml
# Paste dari isi docker-compose.infra.yml (base — postgres, redis, minio, clamav)

5.3 Buat file .env infrastructure

nano /opt/rejki/infra/.env

Isi dengan:

POSTGRES_PASSWORD=<password-kuat-random>
MINIO_ACCESS_KEY=<access-key-kuat>
MINIO_SECRET_KEY=<password-kuat-random>

5.4 Setup JWT keys

# Generate RS256 key pair (jika belum punya)
openssl genpkey -algorithm RSA -out /opt/rejki/keys/private.pem -pkeyopt rsa_keygen_bits:2048
openssl rsa -pubout -in /opt/rejki/keys/private.pem -out /opt/rejki/keys/public.pem
chmod 600 /opt/rejki/keys/*.pem

5.5 Start infrastructure

cd /opt/rejki/infra
docker compose --env-file .env up -d

# Verifikasi semua service running
docker compose ps

# Test PostgreSQL
docker compose exec postgres pg_isready -U rejki

# Test Redis
docker compose exec redis redis-cli ping
✅
Verifikasi Step 5

docker compose ps → postgres, redis, minio, clamav semuanya Up.

7 Deploy Web Frontend

Rejki Web Dashboard (Vue 3) adalah repo terpisah dari backend — rejki-web-dashboard. Image di-build via GitHub Actions, push ke GHCR, lalu compose file milik backend yang melakukan pull & deploy. Arsitektur multi-repo memberi keuntungan: CI independen, deploy terpisah, build hanya yang berubah.

🏗️
Alur Deploy Web (Multi-Repo)

1. Developer push ke rejki-web-dashboard (develop/main)
2. GitHub Actions: lint → build → docker build → push GHCR
3. Workflow SSH ke VPS → docker compose pull rejki-web → up -d
4. Compose file (docker-compose.{dev,prod}.yml) ada di backend repo — dikelola oleh tim backend

GitHub Secrets tidak bisa di-share antar repo. Salin nilai yang sama dari backend repo ke web repo via Settings → Secrets and variables → Actions.

7.2 Dockerfile (Vue 3 + Nginx)

Web menggunakan multi-stage build: Stage 1 build Vue app, Stage 2 serve via Nginx. Ini adalah Dockerfile di root rejki-web-dashboard:

# rejki-web-dashboard/Dockerfile
# Stage 1: Build Vue 3 app
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Serve dengan Nginx
FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY default.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

File default.conf — Nginx config untuk SPA routing:

# rejki-web-dashboard/default.conf
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # Gzip compression
    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_comp_level 6;

    # Cache static assets
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # SPA fallback — semua route ke index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}

7.3 CI/CD Workflow (GitHub Actions)

Buat file .github/workflows/deploy.yml di web repo:

# rejki-web-dashboard/.github/workflows/deploy.yml
name: Build & Deploy Web

on:
  push:
    branches: [develop, main]
  pull_request:
    branches: [develop, main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - uses: actions/checkout@v4

      # ── CI: Lint & Type-check ──
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run type-check
      - run: npm run build

      # ── Docker Build & Push ──
      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GHCR_TOKEN }}

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            type=sha,prefix={{branch}}-

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

      # ── Deploy ke VPS (hanya saat push, bukan PR) ──
      - name: Deploy Web to VPS
        if: github.event_name == 'push'
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USER }}
          key: ${{ secrets.VPS_SSH_KEY }}
          port: ${{ secrets.VPS_PORT || 22 }}
          script: |
            # Tentukan folder target berdasarkan branch
            if [ "${{ github.ref_name }}" = "main" ]; then
              TARGET_DIR=/opt/rejki/prod
            else
              TARGET_DIR=/opt/rejki/dev
            fi

            cd $TARGET_DIR
            docker login ghcr.io -u ${{ github.actor }} --password-stdin <<< "${{ secrets.GHCR_TOKEN }}"
            docker compose --env-file .env pull rejki-web
            docker compose --env-file .env up -d rejki-web
            docker image prune -f
🔄
Kenapa web deploy tapi compose file di backend?

Service rejki-web didefinisikan di compose file backend repo — karena compose file backend yang mendeskripsikan SELURUH stack (termasuk nginx routing). Web repo hanya bertanggung jawab build & push image. Saat web deploy workflow SSH ke VPS, ia menjalankan docker compose pull rejki-web && up -d rejki-web di folder dev/prod yang compose-file-nya sudah ada dari backend.

7.4 Nginx Routing & Container Architecture

Di VPS, traffic dari Cloudflare Tunnel masuk ke Nginx container yang berfungsi sebagai reverse proxy. Nginx meneruskan request:

Path / HostnameDi-forward keContainerPort internal
/api/*API backendrejki-app8080
/notification/*Bun notificationrejki-bun-{env}9000
/* (HTML/JS/CSS)Web dashboardrejki-web-{env}80
/healthHealth checkMasing-masing container—
 
# Contoh: /opt/rejki/dev/nginx.conf
server {
    listen 80;
    server_name _;

    # API → rejki-app
    location /api/ {
        proxy_pass http://rejki-app-dev:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    # Notification → bun-notification
    location /notification/ {
        proxy_pass http://rejki-bun-dev:9000;
        proxy_set_header Host $host;
    }

    # Web Dashboard (Vue 3 SPA)
    location / {
        proxy_pass http://rejki-web-dev:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_buffering off;
    }
}

8 Deploy Observability Stack

Observability stack (metrics, logs, traces) dikirim ke Grafana Cloud (free tier). Stack ini opsional — tapi sangat direkomendasikan untuk monitoring production.

📊
Kenapa Grafana Cloud? Kenapa bukan self-hosted?

Grafana Cloud free tier: 10k metrics series, 50GB logs, 50GB traces — cukup untuk startup. Tanpa maintenance infrastruktur monitoring. File konfigurasi ada di observability/ di repo backend.

8.1 Prasyarat

#PrasyaratDetail
1Akun Grafana CloudDaftar gratis di grafana.com → pilih Free plan
2OpenTelemetry StackBuat Stack di Grafana Cloud → pilih OpenTelemetry → dapatkan endpoint + token
3Docker network rejki-infraPastikan infra sudah di-deploy (Step 5) — observability attach ke network ini

8.2 Setup Environment Variables

Buat folder dan file .env untuk observability di VPS:

mkdir -p /opt/rejki/observability
nano /opt/rejki/observability/.env

Isi dengan kredensial dari Grafana Cloud:

GRAFANA_OTEL_ENDPOINT=https://otlp-gateway-prod-us-central-0.grafana.net/otlp
GRAFANA_OTEL_AUTH_HEADER=Basic <base64-encoded-credentials>

GRAFANA_LOKI_TOKEN=<loki-api-token>
POSTGRES_PASSWORD=<sama-dengan-infra>
⚠️
Cara dapatkan credentials

Grafana Cloud → Stack → OpenTelemetry → Configure → Generate API Key. Copy Endpoint dan Authorization header (format Basic base64). Untuk Loki: Stack → Loki → Configure → Generate API Token.

  1. Buka https://<stack-id>.grafana.net
  2. Sidebar → Explore → pilih data source
  3. Traces: Explore → Tempo → pilih trace yang masuk
  4. Metrics: Explore → Prometheus → query container_memory_usage_bytes
  5. Logs: Explore → Loki → filter berdasarkan container name
✅
Verifikasi Observability

Pastikan data muncul: lihat container_memory_usage_bytes di Prometheus, traces dari service di Tempo, dan log container di Loki. Jika 3 data source muncul → setup sukses.

9 Setup Cloudflare Tunnel

Cloudflare Tunnel menyediakan akses HTTPS tanpa perlu membuka port di firewall.

8.1 Setup Tunnel di Cloudflare Dashboard

  1. Login ke Cloudflare Dashboard → Zero Trust → Networks → Tunnels
  2. Buat tunnel baru (nama: rejki-tunnel)
  3. Pilih: Docker → akan muncul perintah docker run cloudflare/cloudflared ...
  4. Catat Tunnel Token — ini yang akan dimasukkan ke .env

8.2 Setup DNS

Di Cloudflare Dashboard → DNS → Records, tambahkan:

TypeNameTarget
CNAMEdevdev.rejki.id → tunnel
CNAME@rejki.id → tunnel
CNAMEappapp.rejki.id → tunnel

8.3 Konfigurasi Tunnel di Cloudflare Zero Trust

Di halaman Tunnel → Edit → Public Hostname:

HostnameService
dev.rejki.idhttp://localhost:8081 (nginx dev)
rejki.idhttp://localhost:8082 (nginx prod)
app.rejki.idhttp://localhost:8082 (nginx prod)
💡
Cloudflare Tunnel vs port forwarding

Dengan tunnel, VPS tidak perlu membuka port 80/443 di firewall. Semua traffic masuk via tunnel Cloudflare. Lebih aman.

docker logs --tail 50 rejki-nginx-dev

9.4 Checklist Verifikasi

  • PostgreSQL running dan bisa diakses
  • Redis running dan merespon ping
  • MinIO running dan console bisa diakses
  • Backend app merespon di /health (port 8081/8082)
  • Web frontend bisa diakses via browser
  • Cloudflare tunnel active (Zero Trust dashboard)
  • Domain bisa diakses via HTTPS
  • CORS berfungsi (frontend bisa panggil API)

11 Rollback

Jika deploy gagal atau menyebabkan masalah, lakukan rollback:

10.1 Rollback Backend

# 1. Lihat image tag yang tersedia
docker images ghcr.io/rizkirchm97/rejki-backend

# 2. Pull image versi sebelumnya
docker pull ghcr.io/rizkirchm97/rejki-backend:develop-abc1234

# 3. Tag ulang ke develop
docker tag ghcr.io/rizkirchm97/rejki-backend:develop-abc1234 \
  ghcr.io/rizkirchm97/rejki-backend:develop

# 4. Restart
docker compose -f /opt/rejki/dev/docker-compose.dev.yml up -d rejki-app

10.2 Rollback Web

# Pull image versi sebelumnya
docker pull ghcr.io/rizkirchm97/rejki-web:develop-abc1234
docker tag ghcr.io/rizkirchm97/rejki-web:develop-abc1234 \
  ghcr.io/rizkirchm97/rejki-web:develop
docker compose -f /opt/rejki/dev/docker-compose.dev.yml up -d rejki-web

10.3 Rollback via Git

Jika perlu rollback ke commit tertentu dan trigger deploy ulang:

git revert <commit-hash>
git push origin develop
# CI akan build image baru dari hasil revert, lalu deploy
