Phase 1.5 — Notification Contract

Notification Contract

Arsitektur pengiriman notifikasi Rejki: Rust sebagai publisher ke Redis Stream, Bun.js sebagai consumer yang dispatch ke FCM, email, dan simpan ke DB. Fire-and-forget — Rust tidak menunggu delivery selesai.

Phase 1.5 Rust Publisher Bun.js Consumer Redis Streams

🏗️Arsitektur

  Service Rust (auth, iklan, chat, dll)
        │
        │  in-process call
        ▼
  notification-service (Rust)   ← Publisher
        │

        │
        ├─── Email via SMTP / Resend
        │
        └─── PostgreSQL  schema: notification
                 INSERT INTO notification.notifications ...
✅
Kenapa Redis Streams, bukan HTTP langsung?

Fire-and-forget — Rust XADD ke stream dan langsung lanjut. Jika Bun.js sedang restart, event tidak hilang karena tersimpan di Redis. Bun bisa consume setelah kembali online. Tidak ada HTTP timeout yang menghambat request user.

ℹ️
Satu VPS, satu Docker Compose network

Rust app dan Bun.js service berada dalam satu Docker Compose network. Redis tidak expose port ke luar. Bun.js connect ke Redis via service name: redis:6379. Tidak ada latency jaringan eksternal.

Pembagian Tanggung Jawab
KomponenTanggung JawabTidak Melakukan
notification-service Rust Terima event dari service lain → validasi → XADD ke Redis Stream Tidak akses DB notification, tidak panggil FCM, tidak kirim email
bun-notification-service Bun.js XREADGROUP dari Redis → cek idempotency → dispatch FCM/email → tulis DB Tidak expose REST API (kecuali health check), tidak tahu business logic Rust
PostgreSQL DB Simpan notifikasi in-app, idempotency keys, device tokens, user preferences Tidak diakses langsung oleh Rust untuk keperluan notifikasi delivery

Contoh XADD dari Rust
// Rust — notification-service/src/infrastructure/redis_publisher.rs
use redis::AsyncCommands;

pub async fn publish(
    redis: &mut impl AsyncCommands,
    event: &NotificationEvent,
) -> Result<(), anyhow::Error> {
    redis.xadd(
        "notifications_stream",
        "*",  // auto-generate stream ID
        &[
            ("idempotency_key", &event.idempotency_key),
            ("event_type",      &event.event_type),
            ("recipient_id",    &event.recipient_id.to_string()),
            ("actor_name",      event.actor_name.as_deref().unwrap_or("")),
            ("data",           &serde_json::to_string(&event.data)?),
            ("published_at",   &Utc::now().to_rfc3339()),
        ],
    ).await?;
    Ok(())
}
Consumer Group Setup (sekali saat startup)
# Jalankan sekali — idempotent jika group sudah ada
XGROUP CREATE notifications_stream bun-consumers $ MKSTREAM

# Bun.js membaca dengan XREADGROUP
XREADGROUP GROUP bun-consumers bun-worker-1 COUNT 10 BLOCK 2000 STREAMS notifications_stream >

# ACK setelah berhasil diproses
XACK notifications_stream bun-consumers {stream-id}
⚠️
Stream retention — jangan biarkan stream tak terbatas

Tambahkan MAXLEN ~ 10000 di XADD untuk memangkas stream otomatis. Event yang sudah di-ACK tidak perlu disimpan selamanya.

redis.xadd_maxlen("notifications_stream", StreamMaxlen::Approx(10_000), "*", &fields).await?;

🦀Rust — notification-service sebagai Publisher

notification-service Rust berubah peran: tidak lagi menyimpan ke DB atau memanggil FCM. Tugasnya hanya menerima event dari service lain → validasi → XADD ke Redis Stream.

📢Saluran Notifikasi

🔔 In-App

Disimpan di notification.notifications oleh Bun.js. Dibaca client via REST API. Selalu aktif — tidak bisa dimatikan user.

📱 Push (FCM)

Firebase Cloud Messaging via firebase-admin SDK Node.js. HTTP v1 API. User bisa opt-out. Butuh device token yang diregistrasi saat login.

📧 Email

Via SMTP atau Resend API. Untuk event kritis: OTP, reset password, lamaran diterima. User bisa opt-out dari email non-kritis.

🔁Retry & Dead Letter

SaluranMax RetryBackoffGagal Permanen
In-App (DB write)3x1s → 5s → 30sLog error, XACK (jangan block consumer)
Push (FCM)3x5s → 30s → 2mToken invalid → hapus dari DB. Tidak retry.
Email (SMTP)5x1m → 5m → 15m → 1h → 6hTandai failed di DB, log, XACK.

# Message yang gagal setelah max retry dipindahkan ke DLQ
stream name: notifications_dlq

# Bun.js: jika semua retry gagal:
# 1. XADD notifications_dlq * {fields yang sama + error_reason + failed_at}
# 2. XACK notifications_stream bun-consumers {stream-id}

# DLQ diproses manual atau via cron job untuk investigasi
ℹ️
XACK dilakukan setelah semua saluran selesai (berhasil atau gagal permanen)

Jangan XACK sebelum selesai memproses — jika Bun.js crash di tengah, Redis akan otomatis re-deliver ke consumer lain via PEL (Pending Entry List). Bun membaca PEL saat startup untuk handle message yang belum di-ACK.

⚠️
Retry hanya untuk error transient

HTTP 5xx FCM, SMTP timeout → retry. FCM UNREGISTERED (token tidak valid), email bounce → langsung gagal permanen, hapus token/tandai email invalid, jangan retry.

🛡️Deduplication

Redis Streams dengan consumer group menjamin setiap message diproses tepat satu kali per group. Tapi jika Bun crash setelah dispatch tapi sebelum XACK, message akan di-deliver ulang. Idempotency key di DB mencegah double delivery.

-- Bun.js: sebelum proses, cek dan insert idempotency key atomik
INSERT INTO notification.processed_events (idempotency_key, processed_at)
VALUES ($1, now())
ON CONFLICT (idempotency_key) DO NOTHING;

-- Jika rows_affected = 0 → sudah pernah diproses → skip, XACK
-- Jika rows_affected = 1 → lanjut proses

Pembuat key = service Rust pengirim, bukan Bun.js

🗄️DB Schema

Semua tabel berada di schema notification di PostgreSQL yang sama. Migration dikelola oleh Bun.js menggunakan node-pg-migrate atau SQL files yang dijalankan saat startup.

-- notification.notifications — disimpan Bun.js, dibaca Rust REST API
CREATE TABLE notification.notifications (
    id           UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    recipient_id UUID        NOT NULL,
    event_type   TEXT        NOT NULL,
    title        TEXT        NOT NULL,
    body         TEXT        NOT NULL,
    deep_link    TEXT,
    is_read      BOOLEAN     NOT NULL DEFAULT false,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON notification.notifications (recipient_id, created_at DESC);
CREATE INDEX ON notification.notifications (recipient_id) WHERE is_read = false;

-- notification.processed_events — idempotency tracking oleh Bun.js
CREATE TABLE notification.processed_events (
    idempotency_key TEXT        PRIMARY KEY,
    processed_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- TTL cleanup: hapus entry > 7 hari (pg_cron atau cron job di Bun.js)

-- notification.device_tokens — FCM token per user
CREATE TABLE notification.device_tokens (
    id         UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    UUID        NOT NULL,
    token      TEXT        NOT NULL UNIQUE,
    platform   TEXT        NOT NULL,  -- 'android' | 'ios' | 'web'
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON notification.device_tokens (user_id);

-- notification.user_preferences — opt-out per saluran
CREATE TABLE notification.user_preferences (
    user_id       UUID    PRIMARY KEY,
    push_enabled  BOOLEAN NOT NULL DEFAULT true,
    email_enabled BOOLEAN NOT NULL DEFAULT true,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
ℹ️
Migration dijalankan oleh Bun.js, bukan sqlx

Karena Bun.js yang owns schema notification (dia yang write), Bun juga yang jalankan migration-nya saat startup. File SQL disimpan di bun-notification-service/migrations/. Rust notification-service hanya membaca tabel notifications untuk REST API.
