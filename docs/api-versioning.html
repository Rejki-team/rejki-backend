Phase 1.5 — API Versioning & Deprecation

API Versioning & Deprecation

Policy lengkap tentang apa yang dianggap breaking change, kapan membuat versi baru, alur deprecation, dan berapa lama versi lama didukung untuk API Rejki Backend.

Phase 1.5 API Evolution

🧭Prinsip Versioning

URL path versioningVersi dinyatakan di URL: /api/v1/, /api/v2/. Bukan di header (Accept-Version: v2) dan bukan di query param (?version=2). URL versioning paling eksplisit dan mudah di-debug.
Saat ini: hanya /v1/Seluruh Phase 2 dan 3 menggunakan /api/v1/. Tidak ada /v2/ kecuali ada breaking change yang tidak bisa dihindari.
Additive change tidak butuh versi baruMenambah field baru di response, menambah endpoint baru, menambah query parameter opsional — semua ini tidak butuh versi baru.
Versi lama tetap berjalan selama sunsetSaat /v2/ diluncurkan, /v1/ tetap berjalan sampai sunset date yang diumumkan. Tidak ada breaking removal tanpa pemberitahuan.

🆕Kapan Membuat /v2/

Ada breaking change yang tidak bisa dihindariCoba redesign tanpa breaking change terlebih dahulu. Jika tidak bisa (misalnya perubahan fundamental di autentikasi), baru buat /v2/.
Prosedur sebelum membuat /v2/1) Pastikan benar-benar tidak ada cara non-breaking. 2) Diskusikan dengan tim frontend/mobile. 3) Tentukan sunset date untuk /v1/. 4) Baru implementasi /v2/.
/v1/ dan /v2/ berjalan bersamaanKedua versi berjalan di binary yang sama. Kode /v1/ tidak dihapus — hanya ditandai deprecated. Tidak ada server terpisah untuk /v1/.

📢Deprecation Flow

Timeline minimal deprecation sebelum endpoint dihapus:

T+0   Endpoint baru di /v2/ diluncurkan
      Response /v1/ endpoint ditambah header: Deprecation, Sunset
      Release notes diupdate dengan informasi migrasi

T+3 bulan  Pengingat ke tim frontend/mobile
           Monitoring traffic /v1/ — apakah sudah berkurang?

T+6 bulan  Sunset date
           /v1/ endpoint return 410 Gone
           Body: { "error": { "code": "ENDPOINT_GONE", "message": "...", "migrate_to": "/api/v2/..." } }
⚠️
Minimum 3 bulan antara deprecation dan removal

Mobile app tidak bisa force-update semua user sekaligus. User yang tidak update app masih menggunakan versi lama. 3 bulan adalah minimum — pertimbangkan lebih lama jika user base besar.

📋Deprecation Header

Setiap response dari endpoint yang deprecated wajib menyertakan header berikut.

# HTTP Response headers untuk endpoint deprecated
Deprecation: true
Sunset: Sat, 31 Dec 2026 23:59:59 GMT          # tanggal endpoint akan dihapus (RFC 7231 date)
Link: </api/v2/auth/login>; rel="successor-version"  # URL versi pengganti
Response 410 Gone (setelah sunset)
{
  "success": false,
  "error": {
    "code":       "ENDPOINT_GONE",
    "message":    "Endpoint ini sudah tidak tersedia. Gunakan versi baru.",
    "migrate_to": "/api/v2/auth/login"
  }
}

🌅Sunset Timeline

Jenis PerubahanMinimum Sunset PeriodAlasan
Endpoint yang jarang dipakai3 bulanTraffic rendah, dampak migrasi kecil.
Endpoint inti (auth, profil, iklan)6 bulanSemua service dan mobile app bergantung, butuh waktu migrasi lebih lama.
Format response fundamental (envelope, error)12 bulanSemua client perlu update sekaligus — sangat disruptif.

⚙️Implementasi Rust

// Middleware sederhana untuk tambah header Deprecation
pub fn deprecated_endpoint(sunset: &str, successor: &str) -> HeaderMap {
  let mut headers = HeaderMap::new();
  headers.insert("Deprecation", "true".parse().unwrap());
  headers.insert("Sunset", sunset.parse().unwrap());
  headers.insert("Link", format!("<{}>; rel=\"successor-version\"", successor).parse().unwrap());
  headers
}

// Penggunaan di handler yang deprecated
pub async fn old_login_handler(...) -> impl IntoResponse {
  let headers = deprecated_endpoint(
    "Sat, 31 Dec 2026 23:59:59 GMT",
    "/api/v2/auth/login",
  );
  // ... existing handler logic ...
  (headers, existing_response)
}
