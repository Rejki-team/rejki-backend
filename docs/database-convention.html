Phase 1.5 — Database Convention

Database Convention

Standar penamaan, struktur schema, kolom mandatory, soft delete, strategi index, dan aturan migration untuk semua database PostgreSQL di Rejki Backend.

Phase 1.5 PostgreSQL sqlx

🧭Prinsip

Satu schema per serviceSetiap service memiliki schema PostgreSQL sendiri (auth, user_profile, chat, dll). Tidak ada cross-schema JOIN — komunikasi antar service hanya via API.
snake_case seluruhnyaNama tabel, kolom, index, constraint, dan fungsi semuanya lowercase snake_case. Tidak ada camelCase atau PascalCase.
Kolom wajib ada di setiap tabelid (UUID), created_at, updated_at. Tabel yang mendukung soft delete tambah deleted_at.
Migration tidak destruktifTidak ada DROP COLUMN atau DROP TABLE dalam satu migration yang sama dengan perubahan lain. Lakukan secara bertahap dengan migration terpisah.
Tidak ada data logic di DBTrigger, stored procedure, dan computed columns dihindari — logika bisnis ada di application layer (Rust).

📋Kolom Mandatory

Setiap tabel wajib memiliki kolom berikut — tidak ada pengecualian.

-- Kolom mandatory untuk SETIAP tabel
id         UUID        NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY,
created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
updated_at TIMESTAMPTZ NOT NULL DEFAULT now()

-- Tambahan untuk tabel yang mendukung soft delete
deleted_at TIMESTAMPTZ     -- NULL = aktif, NOT NULL = terhapus
⚠️
updated_at tidak update otomatis di PostgreSQL

PostgreSQL tidak punya fitur ON UPDATE CURRENT_TIMESTAMP seperti MySQL. Update updated_at wajib dilakukan di query Rust: UPDATE ... SET updated_at = now() WHERE id = $1. Jangan gunakan trigger.

🗑️Soft Delete

TabelSoft Delete?Alasan
user, profileYa (deleted_at)Data user tidak boleh hilang permanen (PDP, audit)
job_listing, worker_listingYa (deleted_at)Referensi dari lamaran harus tetap valid
message (chat)Ya (deleted_at)Pesan dihapus tetap tampil sebagai "Pesan dihapus"
refresh_token, otp_codeTidak — hard deleteData expired/used tidak perlu disimpan. Hapus langsung.
notification_event (idempotency)Tidak — TTL cleanupHapus otomatis setelah 7 hari via scheduled job
Pola Query Soft Delete
-- Selalu filter deleted_at di query
SELECT * FROM job.job_listing
WHERE id = $1
  AND deleted_at IS NULL;          -- wajib ada ini

-- Soft delete: set deleted_at
UPDATE job.job_listing
SET deleted_at = now(), updated_at = now()
WHERE id = $1
  AND owner_id = $2                 -- IDOR prevention
  AND deleted_at IS NULL;

⚡Index Strategy

Tipe IndexKapan DibuatContoh
Primary key indexOtomatis dibuat untuk id UUID PRIMARY KEY—
Foreign key indexSelalu buat index untuk kolom FK (PostgreSQL tidak buat otomatis)idx_application_user_id pada kolom user_id
Query filter indexKolom yang sering ada di WHERE: email, status, created_atidx_user_email, idx_job_status_created
Partial indexFilter kolom boolean atau status yang nilainya dominan satu nilaiCREATE INDEX idx_job_active ON job_listing(created_at) WHERE deleted_at IS NULL
Composite indexQuery dengan dua kondisi yang selalu muncul bersamaidx_job_city_created untuk filter kota + sort created_at
ℹ️
Urutan kolom di composite index penting

Letakkan kolom dengan selectivity tinggi (filter paling sering) di posisi pertama. Contoh: (status, created_at) lebih baik dari (created_at, status) jika query selalu filter WHERE status = 'active' ORDER BY created_at.

🔄Migration Rules

AturanDetail
Format nama fileV{nomor}_{timestamp}__{deskripsi}.sql — contoh: V1__create_user_table.sql, V2__add_phone_to_user.sql. Gunakan Flyway atau sqlx-migrate.
Satu perubahan per migrationJangan gabungkan create table + add index + alter column dalam satu file. Buat file terpisah per perubahan logis.
Migration tidak boleh dieditSetelah migration di-apply ke staging/prod, file tidak boleh diedit. Buat migration baru untuk perbaikan.
Kolom baru — selalu nullable duluSaat menambah kolom ke tabel yang sudah ada data, buat NULLABLE dulu. Isi data, lalu buat migration baru untuk SET NOT NULL.
Drop column — 3 langkah1) Deploy kode yang tidak menggunakan kolom. 2) Migration: ALTER TABLE DROP COLUMN. 3) Tidak perlu rollback plan jika sudah aman.
Tidak ada data mutation di migrationMigration hanya boleh berisi DDL (CREATE, ALTER, DROP). Data seeding dilakukan di script terpisah, bukan migration file.

📄Contoh Lengkap

-- Contoh tabel lengkap yang mengikuti konvensi
-- File: V1__create_job_listing.sql

CREATE TABLE job.job_listing (
  id           UUID        NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY,
  owner_id     UUID        NOT NULL,                      -- FK ke user-service (via API, bukan FK constraint)
  title        TEXT        NOT NULL,
  description  TEXT        NOT NULL,
  city         TEXT        NOT NULL,
  salary_min   BIGINT,                                    -- nullable: bisa tidak dicantumkan
  salary_max   BIGINT,
  is_active    BOOLEAN     NOT NULL DEFAULT true,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at   TIMESTAMPTZ                                -- soft delete
);

-- Index untuk query yang sering: filter aktif, sort terbaru
CREATE INDEX idx_job_listing_owner   ON job.job_listing(owner_id);
CREATE INDEX idx_job_listing_city    ON job.job_listing(city, created_at DESC);
CREATE INDEX idx_job_listing_active  ON job.job_listing(created_at DESC)
  WHERE deleted_at IS NULL AND is_active = true;    -- partial index
Do vs Don't

✅ Benar

-- FK antar service: hanya via API
-- Tidak ada REFERENCES ke schema lain

-- Kolom boolean
is_active BOOLEAN NOT NULL DEFAULT true

-- Timestamp kolom
deleted_at TIMESTAMPTZ  -- nullable

-- Update query
UPDATE ... SET
  updated_at = now()
WHERE id = $1
  AND owner_id = $2

❌ Salah

-- Cross-schema FK
REFERENCES auth.user(id)

-- Kolom boolean tanpa is_
active BOOLEAN

-- Trigger untuk updated_at
CREATE TRIGGER set_updated_at ...

-- Update tanpa owner check
UPDATE ... SET ...
WHERE id = $1  -- IDOR vulnerability
