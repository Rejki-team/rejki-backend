User Service — Onboarding, KYC & Profil

Dokumen brainstorming teknikal untuk mendesain User Service Rejki di Phase 2, dibangun dari user story dan dipetakan ke standar yang sudah ditetapkan pada Phase 1.5. Fokus: alur registrasi → verifikasi OTP → kelengkapan data diri (KYC) → akun aktif, plus lupa/ubah password dan suspend.

Catatan kepatuhan

User story ini mengumpulkan NIK, Foto KTP, dan Swafoto dengan KTP — termasuk data pribadi yang bersifat spesifik & biometrik wajah di bawah UU PDP No. 27/2022. Karena itu prinsip data minimization, persetujuan eksplisit, enkripsi at-rest, dan kontrol akses ketat menjadi syarat, bukan opsi. Lihat bagian Keamanan & PDP.

⚖️
Catatan K11 — Retensi & UU PDP (hasil riset)

Menyimpan dokumen KYC selama akun aktif tidak melanggar UU PDP No. 27/2022. Pasal 7 menganut prinsip pembatasan penyimpanan: data boleh disimpan selama tujuan pemrosesan masih berlaku — dan identitas terverifikasi adalah dasar keberadaan akun. Kewajiban yang harus dipenuhi: (1) dokumentasikan tujuan & periode retensi, (2) musnahkan data saat akun ditutup / tujuan tercapai / atas permintaan subjek data, (3) sediakan mekanisme penghapusan. Jadi yang berisiko bukan "menyimpan selama aktif", melainkan "menyimpan setelah tak ada tujuan".

🗄️
Catatan K13 — Mengapa database, bukan file/objek (hasil riset)

Data wilayah bersifat relasional & di-query bertingkat (pilih provinsi → tampilkan kota di provinsi itu). Local-storage server tak bisa di-JOIN/validasi; MinIO untuk file biner (KTP/foto), bukan lookup terstruktur. Praktik industri untuk cascading dropdown: tabel ternormalisasi + fetch progresif via API (memuat seluruh ±80rb+ baris ke klien membengkakkan bundle). Validasi kombinasi di server wajib karena form bisa dimanipulasi.

📦
Catatan K7 — Status MinIO (hasil riset, per riset 2026)

MinIO tetap S3-compatible & mendukung presigned URL (cocok untuk alur upload kita). Namun ada perkembangan yang perlu Anda ketahui: rilis komunitas berlisensi AGPLv3; sejak Mei 2025 web console komunitas dipangkas jadi object-browser baca-saja, dan proyek memasuki maintenance mode (Des 2025, rilis komunitas terakhir 15 Okt 2025). Implikasi: MinIO tetap layak sebagai object storage S3-compatible self-hosted, tetapi pertimbangkan: (a) AGPLv3 — penggunaan sebagai dependensi storage tanpa modifikasi umumnya aman, namun perlu kajian legal bila Anda memodifikasi MinIO dan menyajikannya sebagai layanan; (b) alternatif S3-compatible berlisensi lebih longgar bila kelak butuh: SeaweedFS (Apache-2.0), Garage (AGPLv3, ringan), RustFS (Apache-2.0, masih alpha — belum untuk produksi). Karena backend kita memakai API S3 standar (presigned URL), storage dapat ditukar tanpa mengubah kontrak aplikasi.

🗺️
Catatan K6 — Sumber data wilayah (hasil riset)

Tersedia dataset open-source gratis yang mengikuti Kepmendagri terbaru (2025), a.l. cahyadsn/wilayah (kode+data SQL, mengacu Kepmendagri No 300.2.2-2430/2025), emsifa/api-wilayah-indonesia, dan wilayah.id. Rekomendasi: seed tabel referensi di region-service (bukan memanggil API pihak ketiga saat runtime) agar tidak ada dependensi jaringan eksternal & tetap konsisten. Versi dataset (tanggal Kepmendagri) perlu dicatat agar bisa di-update berkala. Lihat Koreksi K13 soal kepemilikan domain.

Koreksi K2 — Domain Client, bukan Redis Streams

Pertanyaan pemilik produk (2026-06-11) menyorot bahwa auth-service & user-service dikompilasi menjadi satu binary (rejki-app) — berbeda dari bun-notification-service yang benar-benar proses terpisah. Karena itu komunikasi antar keduanya cukup lewat Domain Client in-process, dan usulan awal (event Redis Streams) adalah over-engineering untuk transisi status. Revisi ini benar dan diterima.

✅
Bukti dari kode

Pola sudah tersedia: auth-service-client mengekspos trait AuthClient { validate_token() } dan user-service-client mengekspos trait UserClient { get_user_summary(), user_exists() }. Implementasi in-process (AuthInProcessClient) sudah di-wire di rejki-app. Memanggil antar-domain = pemanggilan fungsi biasa: tanpa serialisasi, tanpa kegagalan jaringan, latensi nyaris nol.

KriteriaDomain Client (dipilih)Redis Streams (ditolak untuk kasus ini)
Konteks tepatKomunikasi in-process (satu binary)Komunikasi antar-proses (mis. ke Bun)
Konsistensi saat approve KYCSinkron & kuat — bisa satu alur transaksiEventual — sempat tak sinkron
KompleksitasRendah — pakai trait yang sudah adaTinggi — consumer, retry, idempotency (tak perlu)

🧭
Pemisahan peran yang benar

Ubah status akun (approve/reject KYC, suspend) → Domain Client in-process (K2 revisi). Kirim notifikasi ke perangkat user (US-12 hasil verifikasi) → tetap Redis Streams → Bun → FCM, karena itu memang lintas-proses. K2 lama keliru mencampur dua hal ini.

➡️
Arah dependensi (anti-siklus)

Status akun tetap milik auth-service. Trait AuthClient diperluas dengan method seperti set_account_status(user_id, status) & get_account_status(user_id), yang dipanggil oleh user-service/admin saat KYC disetujui/ditolak. Aliran satu arah: user/admin → auth. Tidak ada ketergantungan melingkar — auth tidak perlu memanggil balik user-service.

Koreksi K13 — Data wilayah sebagai domain mandiri (region-service)

Pertanyaan pemilik produk (2026-06-11): data wilayah tidak hanya untuk perubahan data pengguna, tetapi dipakai banyak service — apakah perlu service & domain client baru? Benar — dan diterima. Menaruhnya di user-service akan memaksa domain lain mengimpor user-service hanya untuk validasi wilayah, yaitu kebocoran batas domain yang justru dihindari (lih. semangat K2).

🔎
Bukti konsumen lintas-domain (dari kode)

Field lokasi ada di keempat service iklan (pekerjaan, pekerja, barang-bekas, pelatihan) — saat ini TEXT bebas. Ditambah user-service (KYC, 4 level wilayah) dan kebutuhan analytics CEO (canvassing per wilayah). Total ≥ 6 konsumen → data wilayah jelas shared domain, bukan milik satu service.

Bentuk region-service (tipis, read-mostly)

Karena data di-seed & read-only bagi konsumen, service ini ramping — mayoritas lookup. Schema sendiri (mis. region), menambah satu pasang crate region-service + region-service-client ke workspace. Tabel region_* yang sebelumnya diusulkan di user_svc dipindah ke schema region-service.

📌

Penyelarasan field lokasi di 4 service iklan (dari teks bebas → region_id berstruktur) ditunda dan dicatat sebagai pertanyaan terbuka untuk brainstorming iklan-service / CEO. Dokumen ini tetap fokus user-service; konsumsi wilayah oleh iklan dibahas terpisah.

📖User Stories (Sumber Kebenaran Brainstorm)

Disalin dari masukan Anda, diberi ID agar mudah dirujuk. Acceptance criteria (AC) adalah usulan turunan—silakan koreksi.

US-01 · Registrasi

Sebagai pengguna, saya ingin mendaftar dengan email, nomor telepon, password, dan persetujuan syarat & ketentuan.

AC: email unik & valid · password memenuhi kebijakan · telepon format E.164 · persetujuan T&C wajib true + dicatat (versi + timestamp) · respons tidak membocorkan apakah email sudah terdaftar (anti-enumeration).
US-02 · Verifikasi OTP

Sebagai pengguna, untuk melanjutkan pendaftaran saya wajib verifikasi OTP yang dikirim ke email saya.

AC: OTP 6 digit, kedaluwarsa (mis. 10 menit) · dibatasi rate & percobaan · sukses → akun naik status dari PENDING_VERIFICATION.
US-03 · Login

Sebagai pengguna, saya dapat login dengan email & password yang terdaftar.

AC: kredensial salah → pesan generik · akun belum terverifikasi/suspended → ditolak dengan kode jelas · sukses → access + refresh token.
US-04 · Wajib Lengkapi Data Diri (KYC) sebelum pakai fitur

Sebagai pengguna yang baru daftar & login, saya tidak dapat memakai fitur apa pun sampai melengkapi: nama lengkap, NIK, tingkat pendidikan, jenis kelamin, tanggal lahir, alamat domisili, negara (default Indonesia), provinsi, kabupaten/kota, kecamatan, kelurahan, foto KTP, swafoto dengan KTP.

AC: token/endpoint fitur menolak akun yang belum ACTIVE · data tersimpan bertahap · setelah lengkap → masuk antrian verifikasi → setelah disetujui admin → ACTIVE.
US-05 · Lupa Password

Sebagai pengguna, saya dapat lupa password dengan otorisasi OTP ke email terdaftar.

AC: minta reset selalu balas sukses (anti-enumeration) · OTP valid → boleh set password baru · semua sesi/refresh token lama dicabut.
US-06 · Ubah Password

Sebagai pengguna login, saya dapat mengubah password dengan otorisasi OTP ke email terdaftar.

AC: verifikasi password lama atau OTP · sukses → refresh token lain dicabut (kecuali sesi aktif, opsional).
US-07 · Suspend oleh Admin

Sebagai akun terdaftar, saya dapat di-suspend oleh admin secara sementara atau permanen.

AC: status suspend ditegakkan saat login & saat validasi token · ada alasan & (untuk sementara) masa berlaku · tercatat di audit log.
US-08 · Perbarui Profil

Sebagai pengguna, saya dapat memperbarui profil saya.

AC: hanya field profil yang boleh diubah mandiri · field KYC terverifikasi tidak boleh diubah diam-diam (perlu verifikasi ulang) — lihat Pertanyaan Terbuka.
US-09 · Foto Profil

Sebagai pengguna, saya dapat menambah/memperbarui foto profil.

AC: upload via mekanisme aman (presigned) · mime & ukuran divalidasi · avatar lama bisa diganti.
US-10 · Lihat Profil

Sebagai pengguna, saya dapat melihat data profil saya yang telah diperbarui.

AC: hanya pemilik melihat data lengkap (termasuk status KYC) · data sensitif (NIK) ditampilkan ter-mask.
US-11 · Update Progres Verifikasi

Sebagai pengguna, saya ingin mendapatkan update proses verifikasi data yang telah saya kirimkan.

AC: status verifikasi dapat dilihat kapan saja (mis. di GET /users/me & layar status) · perubahan status (PENDING_KYC → sedang ditinjau → hasil) tercermin segera · pengguna tahu posisi dirinya dalam alur.
US-12 · Pemberitahuan Verifikasi Selesai

Sebagai pengguna, saya ingin mendapatkan pemberitahuan ketika verifikasi telah selesai (disetujui atau ditolak).

AC: saat admin menyetujui/menolak → kirim notifikasi push + in-app + email (K12: hasil akhir wajib email) berisi hasil · jika ditolak, sertakan alasan & ajakan memperbaiki (hormati cooldown 3 hari kerja, K16) · pemberitahuan tercatat di daftar notifikasi in-app.

🛡️
Penegakan gating

Gating fitur ditegakkan di middleware auth (lapisan 1 pada Authorization Pattern): endpoint fitur (iklan, chat, dst.) menolak token yang status akunnya bukan ACTIVE dengan 403 FORBIDDEN + kode mesin spesifik (mis. ACCOUNT_NOT_ACTIVE). Sesuai K1: status di-embed dalam claim JWT untuk kecepatan, dan untuk hal sensitif (suspend, hasil KYC) kesegaran dijamin lewat cek cepat ke Redis (revocation/refresh-status list). Pembacaan status saat transisi tetap lewat AuthClient in-process (K2 revisi).

⛔Suspend Akun (US-07)

  • Sementara — SUSPENDED_TEMP dengan expires_at; otomatis kembali ACTIVE setelah masa habis (dicek saat login/validasi token).
  • Permanen — SUSPENDED_PERMANENT, expires_at = null.
  • Penegakan — login ditolak; token yang masih hidup ditolak di middleware (cek status via AuthClient atau klaim). Pertimbangkan revoke refresh token saat suspend.
  • Akuntabilitas — wajib reason + created_by (admin) + audit log.
  • Aktor — hanya admin via Web Dashboard (perlu RBAC; lihat PRD Dashboard).
